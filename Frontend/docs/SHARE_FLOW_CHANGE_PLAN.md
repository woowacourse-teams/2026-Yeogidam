# Instagram 공유 플로우 변경 계획

이 문서는 2026-10-09까지 논의한 **변경 목표와 작업 순서**를 기록한다. 변경 전 흐름은 [CURRENT_SHARE_FLOW.md](./CURRENT_SHARE_FLOW.md)에 있다. 구현에 사용한 상태는 `LOGIN_HANDOFF`, `WAITING_FOR_NETWORK`, `WAITING_FOR_AUTH`, `QUEUED`, `REQUESTING`, `API_SUCCEEDED`, `API_FAILED`다.

공유 로그인 연결과 단발 추출 흐름은 구현했다. API 호출 후 오류를 Sentry로 보고하는 작업은 후속으로 미뤘다.

## 목표와 확정한 기준

- 장소 추출 API는 로그인한 사용자만 호출한다. 액세스 토큰이 만료됐어도 리프레시 토큰으로 갱신할 수 있으면 갱신 후 호출한다.
- 잘못된 URL은 “Instagram 콘텐츠만 공유할 수 있어요”라고 안내하고 공유 화면을 닫는다. URL을 저장하거나 API를 호출하지 않는다.
- 미로그인 또는 무효한 리프레시 토큰이 확인되면 공유 화면에 **로그인하고 장소 추출하기** 버튼을 표시한다. 버튼을 누르지 않고 공유 화면을 닫으면 URL을 저장하지 않는다.
- 로그인 버튼을 누르면 로그인 후 이어서 처리할 URL을 기기에 **임시 저장**하고 본 앱 열기를 시도한다. iOS에서 앱이 자동으로 열리지 않으면 직접 앱을 열도록 안내한다. 로그인 성공 후 그 URL로 장소 추출 API를 한 번 호출한다.
- 로그인 화면에서 취소하거나 뒤로 나가면 임시 URL을 즉시 삭제한다. 앱 강제 종료처럼 종료 처리를 실행하지 못한 경우를 위해 오래된 임시 URL의 만료 처리도 둔다. 소셜 로그인 중 외부 인증 화면으로 잠시 이동한 것은 취소로 보지 않는다.
- **API를 호출하기 전** 네트워크 문제로 호출 자체를 시작하지 못한 URL은 기기에 `pending`으로 저장한다. 앱 진입 시 `pending` URL의 **첫 호출**을 시도한다. 그때도 호출할 수 없으면 `pending`을 유지한다.
- **장소 추출 API를 호출한 순간** 해당 URL은 `pending`에서 제외한다. 호출 후 오류가 나거나 응답을 받지 못해도 앱 진입 시 자동 재호출하지 않는다.
- 응답에서 `reelId`를 얻으면 URL 대신 그 ID로 서버 처리 상태를 확인한다. API 호출 후 오류가 나거나 `reelId`를 확인하지 못하면 Sentry에 알린다.
- API 호출에 사용한 URL은 전송 작업에 필요한 동안만 유지하고, 작업 종료 후 공유 결과 저장소와 전송용 임시 파일에서 삭제한다. 메타데이터나 `reelId`는 결과 표시와 진단에 필요한 범위에서 URL과 분리해 보관할 수 있다.

여기서 **재호출하지 않는다**는 뜻은 하나의 공유 건에 대해 장소 추출 API 호출을 한 번만 시작한다는 것이다. 요청을 시작하기 전 기기에 보관한 `pending` URL을 앱 진입 시 처음 호출하는 것은 재호출이 아니다. 호출이 실제로 서버에 도달했는지는 기기가 보장할 수 없으므로, 호출 후 오류가 나면 추출이 누락될 수 있다는 정책이다.

## 케이스별 진행 순서
### A. 잘못된 URL

1. 사용자가 Instagram 콘텐츠가 아닌 URL을 공유한다.
2. 공유 화면이 URL을 검사하고 **“Instagram 콘텐츠만 공유할 수 있어요”**라고 안내한다.
3. 공유 화면을 닫는다. **URL은 저장하지 않고 API도 호출하지 않는다.**

### B. 로그인 상태가 유효한 정상 공유

1. 공유 화면에서 Instagram URL을 확인하고 인증 세션을 확인한다.
2. 백그라운드 전송 작업을 안전하게 등록하고 접수 안내를 표시한 뒤 공유 화면을 닫는다. **이 시점은 API 응답이나 추출 완료가 아니다.**
3. 전송 작업이 장소 추출 API를 호출한다. 호출한 건은 `pending`에서 제외하고 자동 재호출 대상에 넣지 않는다.
4. 정상 응답의 `reelId`를 받는다. 전송 작업이 끝나면 공유 결과 저장소와 전송용 임시 파일의 URL을 삭제한다. URL 없는 `requestId`·`reelId` 등의 결과 정보는 유지할 수 있다.
5. 앱이 `reelId`로 서버 처리 상태를 확인한다. 추출이 완료되면 장소 목록을 새로 조회해 화면에 반영한다.

### C. 액세스 토큰 만료, 갱신 성공

1. 공유 화면에서 만료된 액세스 토큰과 사용 가능한 리프레시 토큰을 확인한다.
2. 토큰을 갱신한다.
3. 갱신한 토큰으로 **B의 2~5단계**를 진행한다. 로그인 버튼을 표시하지 않는다.

### D. 미로그인·재로그인 필요, 버튼을 누르지 않음

1. 공유 화면에서 세션이 없거나 리프레시 토큰이 무효임을 확인한다.
2. **로그인하고 장소 추출하기** 버튼을 보여준다. 이때 URL은 공유 화면이 열려 있는 동안만 사용한다.
3. 사용자가 버튼을 누르지 않고 공유 화면을 닫는다.
4. **URL을 기기에 저장하지 않고 종료한다.** 로그인 후 자동 추출도 없다.

### E. 미로그인·재로그인 필요, 로그인 성공

1. **D의 1~2단계**를 거친다.
2. 사용자가 로그인 버튼을 누른다. 이때 처음으로 URL을 로그인 연결용으로 임시 저장한다.
3. Android는 본 앱을 연다. iOS는 앱 열기를 시도하고, 열리지 않으면 공유 화면에 수동 실행 안내와 **공유 화면 닫기** 버튼을 유지한다. 사용자가 여기담 앱을 열면 로그인 화면으로 이어진다.
4. 사용자가 로그인에 성공한다. 저장한 URL을 전송 작업에 인계하고 장소 추출 API의 첫 호출을 시작한다. 호출 전 네트워크 문제로 시작할 수 없다면 **G의 `pending` 흐름**으로 전환한다.
5. API 호출 이후에는 응답에 따라 **B의 4~5단계** 또는 **H**를 따른다. 임시 URL은 전송에 필요한 동안만 유지하고 작업 종료 시 삭제한다.

### F. 로그인 버튼을 눌렀지만 로그인하지 않고 나감

1. **E의 1~3단계**까지 진행되어 임시 URL이 저장된다.
2. 사용자가 로그인 화면에서 취소하거나 뒤로 나가면 임시 URL을 즉시 삭제한다. API는 호출하지 않는다.
3. 앱 강제 종료처럼 삭제 코드를 실행하지 못한 경우에는 만료된 임시 URL을 나중에 정리한다. 소셜 로그인 중 외부 인증 화면으로 잠시 이동한 것은 취소로 보지 않는다.

### G. API 호출 전 네트워크 문제

1. 공유 화면 또는 로그인 성공 후 전송 준비 중에 네트워크 문제로 장소 추출 API를 **호출하지 못한다**. 토큰 갱신 결과를 네트워크 문제로 알 수 없는 경우도 여기에 포함한다.
2. URL을 기기에 `pending`으로 저장한다. 공유 화면에서 발생했다면 저장을 확인하고 안내한 뒤 공유 화면을 닫는다.
3. 앱에 진입하면 `pending` URL을 확인하고 API의 **첫 호출**을 시도한다.
4. 여전히 네트워크 문제로 호출하지 못하면 URL을 `pending`으로 유지한다. 호출할 수 있으면 그 순간 `pending`에서 제외한다.
5. 호출 후에는 응답에 따라 **B의 4~5단계** 또는 **H**를 따른다. 전송 작업이 끝나면 URL을 삭제한다.

### H. API 호출 후 오류 또는 `reelId` 없음

1. 장소 추출 API 호출은 이미 시작됐으므로 `pending`으로 되돌리지 않는다.
2. 응답 유실·네트워크 오류·API 오류 응답·`reelId` 누락 중 어떤 문제가 발생했는지 확인한다.
3. 후속 Sentry 연동에서는 `requestId`, 플랫폼, HTTP 상태, 오류 유형, 호출 단계 등을 기록한다. 원본 Instagram URL, 공유 텍스트, 인증 토큰은 기록하지 않는다.
4. 자동 재호출하지 않는다. 전송 작업 종료 후 기기에 남은 URL과 전송용 임시 파일을 삭제한다. 필요한 URL 없는 실패 정보만 남긴다.

후속 Sentry 연동에는 오프라인에서 발생한 기록을 나중에 전달할 경로도 포함한다. Sentry는 진단용이며 실패한 추출을 다시 실행하지 않는다. 호출이 실제로 서버에 도달했는지 확인할 수 없는 경우에도 **H의 규칙**을 따른다.

### I. `reelId`를 받았지만 서버의 장소 추출이 실패함

1. **B의 1~4단계**까지 진행한다. URL은 전송 작업 종료 후 이미 삭제된 상태다.
2. 앱이 `reelId`로 서버 처리 상태를 확인하다가 추출 실패 결과를 받는다.
3. 실패 결과를 사용자에게 표시한다. 같은 URL의 API 자동 재호출은 하지 않는다. 서버 추출 실패까지 Sentry에 보고할지는 구현 전에 별도로 정한다.

## URL 보관·삭제 기준

| 보관 목적 | 저장 시작 | 삭제 또는 인계 시점 |
| --- | --- | --- |
| 로그인 연결용 임시 URL | 공유 화면의 로그인 버튼을 누를 때 | 로그인 성공 후 전송 작업 또는 `pending`으로 인계. 명시적 취소·뒤로 가기 시 즉시 삭제. 강제 종료 잔여 건은 만료 처리 |
| 네트워크 대기 `pending` | API 호출 전 네트워크 문제로 호출할 수 없을 때 | 앱 진입 후 API를 실제로 호출할 때 `pending`에서 제외하고 전송 작업에 인계 |
| 진행 중인 전송용 URL | 전송 작업이 URL을 인계받을 때 | 작업 종료 후 공유 결과 저장소와 전송용 임시 파일에서 삭제 |

공유 화면은 API 응답이나 장소 추출 완료를 기다리지 않는다. **전송 작업 등록과 API 호출은 다른 시점**이다. `pending`에서 제외했다는 사실만으로 기기에서 URL이 삭제되는 것도 아니다. Android 작업 입력과 iOS 백그라운드 업로드 본문처럼 전송 중 필요한 사본을 작업 종료 시 정리한다.

## 구현을 위해 정리한 작업 순서

1. **상태와 저장 계약 정리:** 로그인 연결용 임시 URL, 호출 전 네트워크 `pending`, 호출이 시작된 결과 메타데이터를 구분한다. 저장된 URL과 URL 없는 결과의 삭제 조건을 명시한다. 여러 공유 건은 `requestId`별로 관리한다.
2. **공유 화면의 인증 분기 변경:** 변경 전처럼 URL을 먼저 영구 저장하지 않고 URL 검증과 인증 확인을 수행한다. 미로그인·무효 토큰이면 로그인 버튼을 표시한다. 버튼을 누른 건만 임시 저장해 본 앱 로그인으로 인계한다. 잘못된 URL은 안내 후 종료한다.
3. **로그인 완료 연결:** 앱의 기존 로그인 성공 경로에서 로그인 연결용 URL을 찾아 첫 API 호출을 시작한다. 명시적 취소·뒤로 가기 시 삭제하고 강제 종료 잔여 건의 만료 처리를 추가한다. 소셜 인증 화면 이동은 취소로 분류하지 않는다.
4. **호출 전 네트워크 대기:** API 호출을 시작할 수 없는 네트워크 문제만 `pending`으로 저장한다. 앱 시작·재활성화 시 `pending`을 확인하고 네트워크가 가능하면 첫 호출을 시작한다. 호출 전에 다시 네트워크가 불가능하면 URL을 유지한다.
5. **호출 시작 후 단발 처리:** 네이티브 전송 작업이 장소 추출 API를 호출할 때 `pending`을 제거하고 이후 앱 진입 시 같은 건을 다시 등록하지 않는다. Android WorkManager의 기존 API 오류 자동 재시도와 iOS의 재등록 조건을 새 정책에 맞춘다. 작업 종료 후 URL을 담은 로컬 결과와 임시 파일을 정리한다.
6. **결과 표시와 진단:** `reelId`를 받은 건은 URL 없이도 처리 상태를 조회하도록 연결한다. 호출 후 응답 유실·API 오류·`reelId` 누락을 Sentry로 보고하고, URL이 남지 않도록 확인한다. Sentry 연동은 후속 작업으로 남겨 두었다.
7. **검증:** Android와 iOS에서 유효하지 않은 URL, 버튼 없이 공유 화면 닫기, 로그인 성공·취소·외부 소셜 인증 이동, 토큰 갱신 성공·무효·네트워크 오류, 오프라인 `pending` 후 앱 진입, API 호출 후 응답 유실, `reelId` 유무, 앱 강제 종료를 확인한다.

## 구현 후 확인할 항목

- 로그인 연결용 임시 URL은 `LOGIN_HANDOFF` 상태로 30분간 보관하고, 명시적으로 취소하면 즉시 삭제한다. 로그인 세션이 확인되면 네트워크 대기 상태로 넘겨 이 만료 대상에서 제외한다.
- iOS 공유 확장에서 본 앱을 직접 여는 동작은 시스템에서 보장되지 않는다. 로그인 버튼을 누르면 URL을 저장하고 앱 열기를 시도한다. 열리지 않으면 수동 실행 안내와 **공유 화면 닫기** 버튼을 표시하고 자동으로 닫지 않는다. 실제 기기에서 이 연결 경험을 확인해야 한다.
- 서버의 로그인 필수 검사 위치와 응답 계약. 공유 저장은 Spring Boot `POST /api/v1/shares`(로그인 필수)로 바뀌었고 토큰이 없거나 무효하면 401(`AUTH401_004`, `AUTH401_001`)을 돌려준다. 공유 확장은 401 응답을 `AUTH401_001`로 기록하고, 앱은 이를 추출 실패가 아닌 로그인 만료로 안내한다. 서버에 멱등키가 없어 같은 링크를 다시 보내면 공유가 새로 생긴다.
- 공유가 여러 건 연속으로 들어오면 `requestId`별로 보관한다. 화면에는 선택된 한 건을 표시하므로 연속 공유 UX를 실제 기기에서 확인해야 한다.
- `reelId`를 받은 뒤 서버의 장소 추출 자체가 실패했을 때 Sentry 보고 여부는 아직 정하지 않았다.
- Sentry 연동과 `SENTRY_DSN` 설정은 후속 작업이다. 현재 커밋의 실패 결과는 사용자 안내까지만 연결한다.
