# 스프린트 2 안드로이드 요구사항

## 개요

이번 스프린트에서는 운영 중인 앱을 빠르게 진단하기 위한 **개발자 도구**와, 구성 변경이나 시스템의 프로세스 종료가 발생해도 사용자의 작업을 지키기 위한 **상태 보존**을 적용했다.

여기담은 React Native로 구성되어 있어 화면 상태는 React 상태와 기기 저장소를 함께 사용한다. 화면을 다시 그리는 데 필요한 작은 값만 Saved State 성격의 임시 저장소에 두고, 화면을 닫은 뒤에도 유지할 데이터만 Persistent Storage에 저장했다. 서버에서 다시 받을 수 있는 목록과 상세 객체는 저장하지 않았다.

---

## 1. 개발자 도구

### 도입 배경

테스트 중인 앱의 버전이나 연결된 서버를 화면에서 확인할 수 없으면 잘못된 빌드로 테스트하거나, 문제를 재현하기 위해 설정 파일과 로그를 다시 확인해야 한다. 이후 스프린트에서 원격 설정 갱신, 업데이트 흐름, 딥링크 실행, 인증 만료 등을 반복해서 확인하려면 이를 한곳에서 재현할 수 있는 진입점도 필요하다.

이를 위해 debug 빌드에만 개발자 도구 화면을 추가했다. 이번 스프린트에는 앱과 서버 환경을 식별하는 기본 정보만 제공하고, 이후 요구사항에 필요한 기능을 같은 화면에 확장할 수 있도록 구성했다.

### 들어가는 방법

1. 여기담 개발 앱을 실행한다.
2. 하단의 **마이페이지** 탭으로 이동한다.
3. 설정 목록 아래의 **개발자 도구**를 누른다.

`개발자 도구` 메뉴와 화면은 debug 빌드에만 존재한다. 로컬 개발 앱은 운영 앱과 동시에 설치할 수 있도록 애플리케이션 ID에 `.dev`가 붙는다.

| 빌드 | 애플리케이션 ID | 개발자 도구 |
| --- | --- | --- |
| debug | `com.yeogidamm.app.dev` | 메뉴와 화면 모두 포함 |
| release | `com.yeogidamm.app` | 메뉴와 화면 모두 제외 |

### 화면에서 확인할 수 있는 정보

| 항목 | 로컬 debug 빌드 표시값 | 확인 목적 |
| --- | --- | --- |
| 앱 버전 | `1.1.0-dev` | 현재 테스트 중인 앱의 `versionName` 확인 |
| 빌드 번호 | `2` | 같은 앱 버전 안에서 `versionCode`로 결과물 구분 |
| 빌드 타입 | `debug` | 개발용 빌드와 배포용 빌드 구분 |
| 서버 환경 | `development` | 개발 서버와 운영 서버 중 현재 연결 대상 확인 |

앱 버전과 빌드 번호는 Android의 `BuildConfig.VERSION_NAME`, `BuildConfig.VERSION_CODE`를 사용한다. 서버 환경은 빌드 시 환경 파일에서 주입하는 `APP_ENV`를 사용한다. GitHub Actions에서 생성하는 빌드는 `APP_VERSION`과 `APP_BUILD_NUMBER`가 주입되므로 로컬 기본값 대신 배포 시 입력한 값이 표시된다.

### debug 전용 분리 방식

개발자 도구는 Android의 `debug` 소스셋에 분리했다. 개발자 도구 화면, 진입을 위한 네이티브 모듈, debug 전용 Manifest 선언을 `android/app/src/debug`에 두고 release 소스셋에서는 이를 참조하지 않는다. React Native 화면에서는 `__DEV__`일 때만 마이페이지에 진입 메뉴를 렌더링한다.

진입 메뉴만 숨기지 않고 소스셋을 분리한 이유는 다음과 같다.

- release 결과물에 개발자 도구의 Activity와 리소스가 들어가는 것을 빌드 단계에서 막을 수 있다.
- 이후 추가할 원격 설정 덮어쓰기, 테스트 딥링크, 인증 만료 재현 기능이 일반 사용자에게 노출되는 것을 방지할 수 있다.
- debug 전용 기능을 한곳에 모아 운영 코드와의 경계를 명확하게 유지할 수 있다.

### release 결과물 검증

debug와 release 결과물을 각각 생성한 뒤 진입 가능 여부와 APK 내부 포함 여부를 확인했다.

```bash
cd android
./gradlew assembleDebug assembleRelease
```

검증에는 로컬 기본 버전 `1.1.0`, 빌드 번호 `2`를 사용했다.

| 검증 항목 | debug 결과 | release 결과 |
| --- | --- | --- |
| 마이페이지의 개발자 도구 메뉴 | 노출됨 | 노출되지 않음 |
| 개발자 도구 화면 접근 | 가능 | 불가능 |
| 개발자 도구 Activity | 포함됨 | 포함되지 않음 |
| 개발자 도구 전용 리소스 | 포함됨 | 포함되지 않음 |

release APK인 `android/app/build/outputs/apk/release/app-release.apk`를 Android Studio의 APK Analyzer로 열어 개발자 도구 Activity 이름과 화면 고유 문자열인 `개발자 도구`를 검색했다. 검색 결과가 없었고, release Manifest에도 개발자 도구 Activity가 병합되지 않은 것을 확인했다.

### 선택한 방법의 한계

마이페이지 진입 메뉴는 `__DEV__` 조건으로 한 번 더 제한하지만, 이 조건만으로 코드 제외를 보장하지는 않는다. 실제 제외 여부는 debug 소스셋 분리와 release APK 분석 결과를 기준으로 판단했다.

또한 개발자 도구에서 앱 프로세스를 직접 종료하는 기능은 제공하지 않았다. 앱 안에서 자기 프로세스를 종료하는 동작은 Android 시스템이 백그라운드 앱을 종료하는 상황과 같지 않기 때문이다. 프로세스 종료에 따른 상태 복원은 `adb shell am kill`로 별도 검증했다.

## 2. 상태 보존

### 저장 기준

상태가 살아 있어야 하는 범위에 따라 다음과 같이 저장 위치를 나눴다.

| 저장 수단 | 적용 기준 | 예시 |
| --- | --- | --- |
| React 메모리 상태 | 현재 화면이 유지되는 동안만 필요한 값 | 로딩 여부, 오류 메시지, 모달 노출 여부 |
| Saved State | 구성 변경과 프로세스 종료 뒤 화면 복원에 필요한 작은 값 | 검색어, 선택한 장소 ID |
| Persistent Storage | 화면을 닫거나 앱을 다시 실행해도 유지할 값 | 최근 검색어, 로그인 세션, 가이드 완료 여부 |

React Native에서는 검색어와 같은 입력값을 임시 상태 저장 키로 직렬화해 복원하고, 사용자가 화면을 명시적으로 닫으면 해당 키를 제거했다. 최근 검색어처럼 다음 방문에도 필요한 값은 `AsyncStorage`에 계속 유지했다.

목록 전체와 API 응답 객체는 Saved State에 넣지 않았다. 장소 목록의 영구 원본은 서버이며, 저장된 검색어 또는 ID를 이용해 다시 불러온다. 이 방식으로 복원에 필요한 정보는 유지하면서 저장 크기가 커지는 문제를 피했다.

### 화면별 상태 목록

| 화면 | 상태 | 살아남아야 하는 상황 | 저장 수단 | 이유와 원본 |
| --- | --- | --- | --- | --- |
| 지도 | 입력 중인 검색어 | 구성 변경, 프로세스 종료 | Saved State | 사용자가 직접 입력한 작은 문자열이다. 검색 결과 목록은 저장하지 않고 검색어로 다시 계산한다. |
| 지도 | 선택한 장소 | 구성 변경, 프로세스 종료 | Saved State에 장소 ID 저장 | 장소 객체 전체 대신 ID만 저장한다. 장소 상세 정보의 원본은 저장 장소 API이다. |
| 보관함 | 현재 검색어 | 구성 변경, 프로세스 종료 | Saved State | 검색 중 프로세스가 종료되어도 같은 검색 화면을 복원한다. 화면을 직접 닫으면 제거한다. |
| 보관함 | 최근 검색어 | 구성 변경, 프로세스 종료, 화면을 닫고 다시 열기 | Persistent Storage (`AsyncStorage`) | 다음 방문에도 검색 기록을 제공해야 하는 사용자 데이터이다. 기기 저장소가 원본이다. |

### 원본(Source of Truth) 기준

- 지도와 보관함에서 검색 중일 때는 Saved State의 검색어가 현재 UI 상태의 원본이다.
- 장소 목록과 장소 상세 정보는 서버 응답이 원본이다. Saved State에는 장소 ID만 두고 복원 시 데이터를 다시 조회한다.
- 최근 검색어는 서버에 저장하지 않으므로 `AsyncStorage`가 원본이다.
- API 응답, 검색 결과 목록, 이미지 데이터처럼 다시 가져올 수 있거나 크기가 큰 값은 Saved State에 저장하지 않는다.

### 검증 방법

검증은 Android debug 앱 `com.yeogidamm.app.dev`, 앱 버전 `1.1.0-dev`, 빌드 번호 `2`를 기준으로 진행했다.

#### 1. 구성 변경

각 화면에 테스트 값을 입력한 뒤 다크 모드를 전환했다. `MainActivity`가 `uiMode`, `orientation`, `screenSize` 등의 구성 변경을 처리하는 동안 React 화면 상태가 유지되는지 확인했고, Activity 또는 JS 화면이 다시 구성되는 경우에도 저장한 상태로 복원되는지 확인했다.

#### 2. 시스템의 프로세스 종료

각 화면에 테스트 값을 입력한 뒤 홈 버튼으로 앱을 백그라운드에 보내고 다음 명령을 실행했다.

```bash
adb shell am kill com.yeogidamm.app.dev
```

최근 앱 화면에서 여기담을 다시 선택한 뒤 이전 화면과 상태가 복원되는지 확인했다. `adb shell am force-stop`은 사용자가 앱을 강제 중지한 별도 상황이므로 사용하지 않았다.

#### 3. 화면을 닫고 다시 열기

뒤로 가기 또는 다른 탭으로 이동해 화면을 명시적으로 닫은 뒤 같은 화면을 다시 열었다. 화면 세션에서만 필요한 임시 상태는 초기화되고, Persistent Storage 대상으로 정한 최근 검색어는 유지되는지 확인했다.

### 검증 결과

| 화면·상태 | 구성 변경 | 프로세스 종료 | 화면을 닫고 다시 열기 | 결과 |
| --- | --- | --- | --- | --- |
| 지도 검색어 `성수` | 유지 | 유지 | 초기화 | 기대한 범위와 동일하게 동작 |
| 지도에서 선택한 장소 | 유지 | 장소 ID를 기준으로 복원 | 초기화 | 상세 객체를 저장하지 않고 다시 조회 |
| 보관함 현재 검색어 `카페` | 유지 | 유지 | 초기화 | 명시적으로 화면을 닫으면 임시 상태 제거 |
| 보관함 최근 검색어 `카페` | 유지 | 유지 | 유지 | `AsyncStorage`에서 다시 로드 |

구성 변경과 프로세스 종료 뒤에는 검색어가 유지됐다. 장소 상세는 저장해 둔 장소 ID로 다시 조회했으며, 목록 전체를 Saved State에 넣지 않아 저장 크기가 커지지 않았다. 사용자가 화면을 직접 닫았을 때는 지도 검색과 보관함 현재 검색어가 초기화됐고, 다음 방문에도 필요한 보관함 최근 검색어만 남았다.

### 적용 결과와 한계

사용자가 직접 입력한 값은 프로세스 종료에도 잃지 않으면서, 다시 조회할 수 있는 데이터는 최소 식별자만 저장하는 구조로 분리했다. 상태별 수명과 원본이 명확해졌고, 이후 인증 만료 후 원래 화면으로 돌아오는 기능에도 같은 복원 방식을 사용할 수 있다.

프로세스 복원 직후에는 서버 데이터를 다시 불러오는 동안 로딩 상태가 잠시 보일 수 있다. 네트워크가 없는 경우 검색어와 장소 ID 같은 최소 정보는 복원되지만 최신 상세 데이터는 가져올 수 없으므로 기존 오류 화면에서 재시도를 제공한다.

## 3. 시연 자료

제출 문서에는 다음 순서로 촬영한 화면 또는 영상을 함께 첨부했다.

1. 마이페이지에서 개발자 도구로 진입하고 앱 버전, 빌드 번호, 빌드 타입, 서버 환경을 확인하는 화면
2. release 앱의 마이페이지에 개발자 도구 메뉴가 나타나지 않는 화면과 APK Analyzer 검색 결과
3. 지도에서 `성수`를 검색한 뒤 앱을 백그라운드로 보내고 `adb shell am kill`을 실행한 후 검색어가 복원되는 영상
4. 보관함에서 `카페`를 최근 검색어에 추가하고 화면을 닫았다가 다시 열어 검색 기록이 유지되는 영상
