# 수파베이스에서 스프링으로: 여기담 백엔드 마이그레이션 회고

여기담은 인스타그램 릴스를 공유하면 장소를 추출해 지도에 모아 주는 앱이고 백엔드는 수파베이스(BaaS) 위에서 엣지 펑션으로 돌고 있었다.
이걸 자바 스프링부트로 옮기는 참조 구현을 만들면서 부딪힌 문제들과 그때마다 세운 기준을 기록한다.
전제 조건은 우테코 미션 방식이었다. 콘솔 수준에서도 도메인이 통째로 돌아가게 객체를 먼저 모델링하고, 객체지향 생활체조(else와 switch 금지, 메서드 10줄, 원시값 포장, 일급 컬렉션)를 지키고, DB는 JPA 없이 JDBC RowMapper로 붙이되 도메인 객체와 DB 표현을 분리한다.

## 1. 링크 판별: 문서보다 실측을 믿는다

첫 도메인은 가장 작아 보이는 곳, "지원하는 링크인가?"에서 시작했다. 그런데 작지 않았다.

- shortcode는 11자라고 알려져 있었지만 Meta 공식 문서의 예시가 10자였고 지금도 살아 있는 게시물이었다. 운영 DB 383건이 전부 11자인 것은 최근 데이터에 치우친 표본일 뿐이었다. 길이 검증을 뺐다.
- 복수형 `/reels/` 경로는 받기로 했다가 같은 날 뒤집었다. 모바일 앱의 공유 버튼은 그 형태를 만들지 않고 PC 웹에서만 생긴다는 것을 확인해서다.
- "shortcode에 따라 p와 reel이 리다이렉트된다"는 가설은 실제 HTTP 요청 40회로 검증했더니 틀렸다. 어떤 조합도 리다이렉트 없이 200이었고 정답 경로는 응답 본문의 og:url에만 있었다. 덕분에 "shortcode만 보관하고 경로는 버린다"는 설계가 확정됐다.

여기서 세운 기준이 이후 전체를 지배했다. 관측된 것부터 만들고, 관측되지 않은 것은 로깅으로 미루고, 문서와 통념은 실측으로 확인한다. 실패 사유 enum을 운영에서 관측된 4종으로 시작한 것도 문자셋 검증을 base64url 규격에 근거해 남긴 것도 같은 기준이다.

## 2. 사실과 해석을 분리한다

"어차피 사용자한테 받는 URL인데 왜 파싱해서 shortcode만 남기냐"고 팀원이 물었다. 논쟁의 결론은 분리였다. 원본 URL은 사용자가 준 사실이고 shortcode는 우리의 해석이다. 해석 규칙은 바뀔 수 있으므로(예: 단축링크 지원 추가) 사실은 그대로 보관하고 해석은 중복 판정과 재사용의 키로 쓴다.

이 구분은 이후 곳곳에서 다시 나타났다. 추출된 장소 행은 파이프라인의 사실이고 저장·버림 결정은 사용자의 해석이다. 버림을 물리 삭제로 구현하면 해석을 기록하려다 사실을 지운다는 결론에 이르러 3값 결정 상태(UNDECIDED, SAVED, DISCARDED)를 뒀다. 캡션도 추출의 입력이었던 사실이라 함께 보관하기로 했다.

## 3. 상태는 조합이 있을 때만 객체로

추출 상태를 처음에는 enum 필드로 관리했다. 전이마다 상태 확인 if가 붙고, 필드 절반이 상태에 따라 null이 되고, 정리 코드 한 줄을 잊으면 모순 데이터가 생기는 구조였다. 행위 4종과 상태 3종의 조합이 있다는 것이 문제의 뿌리라 상태를 Extraction 인터페이스와 구현체 3개로 추상화했다. 전이 규칙이 구현체 안에 응집되고 짝 데이터(성공의 장소, 실패의 사유)가 생성자 필수 인자가 되면서 모순 조합이 타입 수준에서 불가능해졌다. else와 switch도 소스에서 사라졌다.

반면 장소 결정 상태(PlaceDecisionStatus)는 enum으로 뒀다. 전이 guard가 조건부 UPDATE 한 줄로 끝나고 상태별로 갈리는 행위 조합이 없어서다. 같은 프로젝트에 두 방식이 공존하는 것 자체가 "조합이 있으면 상태 객체, 없으면 enum"이라는 기준의 적용 결과다.

## 4. 검증은 실패시킬 가치가 있는 값에만

외부 API가 주는 값은 잘못됐을 때 되돌려 줄 상대가 없다. 검증에 실패시키면 할 수 있는 일이 그 장소를 버리는 것뿐이므로 버릴 가치가 있는 값만 검증하기로 했다. 이름(카드·검색·핀이 전부 걸림), 좌표(틀린 핀은 안 보이는 것보다 나쁨), 지번 주소, 외부 장소 식별자(중복 제거 키)는 검증하고 전화번호와 카테고리와 사진은 담기만 한다. 형식이 아쉬운 표시용 값(도로명, 카카오맵 URL)은 예외 대신 null 정규화가 도구다.

검증 시점도 옮겼다. 값 객체 검증이 조회 때 처음 돌면 불량 데이터가 조용히 저장됐다가 며칠 뒤 사용자 클릭에서 500으로 터진다. 저장 직전에 값 객체 생성을 한 번 통과시키는 검문을 둬서 불량 장소는 그 미디어에서만 빠지고 원인과 증상이 같은 시점에 만나게 했다.

## 5. 이름의 여정, 그리고 치환 사고

이름은 세 번 크게 움직였다. Reel은 게시글(/p/)도 담게 되면서 Meta 어휘 그대로 InstagramMedia가 됐다. 결정 상태의 어휘는 PlaceReviewStatus에서 PlaceDecisionStatus로, PENDING에서 UNDECIDED로, reviewed_at에서 decided_at으로, 클래스부터 DB 컬럼까지 한 축으로 통일됐다.

Reel 개명 때 사고가 하나 있었다. 단어 경계 일괄 치환이 InstagramUrl의 경로 정규식(`p|reel`)과 테스트 URL 속 "reel"을 둘 다 바꿔버려서 테스트는 양쪽이 같이 오염된 채 통과하고 실제 인스타그램 URL은 거부되는 상태가 잠깐 있었다. 부팅 후 실제 HTTP 호출로 도는 스모크 테스트가 잡았다. 구현과 테스트가 함께 오염되면 테스트는 침묵한다는 것, 그래서 대규모 치환 뒤에는 실제 실행 검증이 필수라는 교훈이 남았다.

## 6. 다중 사용자, 전역 장소, 재추출 방지

사용자 개념이 들어오자 "장소별 저장 상태를 place 테이블에 두면 여러 사용자를 어떻게 구분하냐"는 물음이 구조를 갈랐다. 답은 사실과 해석의 분리를 테이블로 물리화하는 것이었다. 장소 사실은 전역 place 테이블 한 곳(카카오 place id로 중복 제거), 사용자별 해석은 media_place 연결 행(결정 상태와 시각)에 둔다. 재추출 방지는 shortcode와 파이프라인 버전으로 완료본을 찾아 연결만 복사하는 방식이라 다른 사용자가 다른 경로(/p/와 /reel/)로 같은 게시물을 공유해도 추출은 한 번만 돌고 결정은 서로 전염되지 않는다. A의 저장과 B의 버림이 같은 장소 위에 공존하는 것을 실제 두 사용자 시나리오로 검증했다.

## 7. 리뷰가 잡아낸 것들: 테스트가 못 보는 결함

멀티 에이전트 리뷰(찾기와 반박 검증의 2단계)를 구현 단위마다 돌렸고 단위 테스트가 침묵하는 결함들이 거기서 나왔다.

- @Transactional 안에서 @Async 파이프라인을 디스패치하면 커밋 전에 실행돼 미디어가 EXTRACTING에 영구 고착될 수 있다 → afterCommit 콜백으로 이동
- 동시 재시도 두 건이 모두 통과하는 read-then-write 경쟁 → 조건부 UPDATE로 한 건만 통과
- 동시 추출이 같은 신규 장소를 넣는 find-then-insert 경쟁이 정상 추출을 UNEXPECTED 실패로 둔갑시킴 → 유니크 위반 시 재조회 폴백
- 서버 재기동으로 파이프라인 작업이 유실되면 EXTRACTING에서 빠져나올 길이 없음 → 기동 시 복구 러너
- 저장 해제 UPDATE의 자기 참조 서브쿼리가 H2에서는 돌지만 MySQL에서는 오류 1093으로 항상 실패 → 파생 테이블로 감쌈

공통 교훈은 하나다. 상태와 시간이 얽힌 결함은 단위 테스트가 아니라 실제 실행(스모크)과 적대적 검증(반박 리뷰)이 잡는다.

## 8. 방향을 다시 세우다: 도메인이 먼저다

운영 스키마를 참고 기준으로 삼고 이관하다 보니 어느새 테이블이 먼저 서고 도메인이 검증기 역할로 밀리는 역전이 생겼다. 소유자와 결정 상태가 도메인에 없고 SQL에만 있었다. 장기(java-janggi) 구조를 기준 삼아 방향을 되돌렸다. 도메인 관계를 먼저 완성하고(소유자는 OwnerId로 집합체 간 id 참조, 원본과 해석은 SharedLink 한 쌍, 표시용 값은 MediaMetadata로 들되 검증하지 않음, 추출 사실과 결정은 ExtractedPlace 한 쌍), 결정 전이를 도메인 행위(decidePlaces)로 옮겼다. 남은 것은 저장 포트(Repository 인터페이스)와 WriteMapper/ReadMapper로 DAO를 infra 안에 숨기는 마지막 정렬이다. "도메인 관계를 먼저 형성하고, 영속화할 값은 매퍼가 고른다"가 최종 원칙이다.

## STAR 요약

**Situation.** 수파베이스 BaaS로 운영 중인 여기담 백엔드(릴스 공유 → AI 장소 추출 → 지도 저장)를 자바 스프링부트로 이관하는 참조 구현을 맡았다. 운영에는 383건의 미디어와 사용자 결정 849건이 쌓여 있었고 우테코 방식(POJO 우선, 생활체조, JDBC RowMapper, 도메인과 DB 분리)이 전제였다.

**Task.** 링크 판별부터 추출 파이프라인, 사용자별 장소 결정, 지도 조회까지 US-01과 US-02 전 구간을 도메인 중심으로 재설계하고 다중 사용자와 재추출 방지까지 갖춘 동작하는 수직 슬라이스를 만들어야 했다.

**Action.** 결정마다 실측(운영 DB 수치, HTTP 실험 40회, Meta 문서 반례)을 근거로 세우고 ADR과 설계 문서로 남겼다. 상태는 조합 기준으로 객체와 enum을 가려 썼고 사실과 해석을 분리하는 원칙을 URL 보관부터 전역 장소와 연결 테이블 구조까지 일관되게 적용했다. 구현 단위마다 부팅 스모크와 반박 검증형 멀티 에이전트 리뷰를 돌려 동시성과 트랜잭션 결함 다섯 건을 상용 전에 제거했고 구조가 DB 주도로 기울었을 때 장기 프로젝트를 기준 삼아 도메인 관계 완성으로 되돌렸다.

**Result.** 두 사용자가 같은 게시물을 다른 경로로 공유해도 추출은 한 번만 돌고 결정은 독립인 전 구간이 실제 호출로 검증됐다. 도메인 소스에는 else와 switch가 없고, 모순 상태는 표현할 타입이 없으며, 원칙들은 CLAUDE.md와 문서 6편(ADR 1, 설계 3, 회고 2)으로 남아 다음 결정의 기준이 됐다. 테스트가 침묵하는 결함을 실행과 적대적 리뷰로 잡는다는 검증 체계도 함께 남았다.
