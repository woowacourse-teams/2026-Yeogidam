# ADR-02. 게시글 삭제와 게시물 장소 선택

- **상태** 결정
- **날짜** 2026-11-06
- **관련 이슈** #550(부모), #551, #552, #553, #554, #555

---

## 배경

UT에서 히스토리 목록의 게시글을 지우고 싶다는 의견이 나와, 11-05 회의에서 게시글 삭제 API를 만들기로 했다.
같은 회의에서 보관함 게시물 탭(#535)의 게시물 상세에 추출된 장소를 모두 보여 주고, 장소마다 체크로 저장 여부를 고르는 화면을 정했다.

지금 테이블은 아래처럼 나뉘어 있다.

| 테이블 | 담는 것 | 삭제할 때 |
|---|---|---|
| `media` | 게시물. 여러 회원이 함께 쓰는 캐시 | 회원 탈퇴에도 남는다 |
| `shared_media` | 회원이 게시물을 공유한 기록. 히스토리 카드 하나 | 회원 탈퇴 때 CASCADE |
| `media_places` | 게시물에서 추출한 장소. 여러 회원이 함께 쓴다 | 남는다 |
| `saved_places` | 회원의 보관함 장소. `(member_id, place_id)` UNIQUE | 장소 삭제 API가 지운다 |
| `shared_media_saved_places` | 보관함 장소를 어느 공유에서 저장했는지 | `saved_places`, `shared_media`를 지우면 CASCADE |
| `folder_saved_places` | 폴더에 담은 보관함 장소 | `saved_places`를 지우면 CASCADE |
| `shared_media_reports` | 실패 공유의 제보 | `shared_media`를 지우면 CASCADE |

## 결정

### 1. 게시글을 지우면 남은 게시글에 없는 장소도 보관함에서 뺀다

회의에서 「게시글을 지우면 연관된 장소도 장소 리스트에서 뺀다」를 골랐다(포도, 두부, 정콩, 러키).

- 지우지 않은 다른 게시글에도 있는 장소는 남긴다. `saved_places`는 회원과 장소마다 레코드가 하나뿐이라, 지우면 건드리지 않은 다른 게시글의 체크까지 풀리기 때문이다.
- 다른 게시글에도 있는 장소는 지우지 않은 공유와 공유 연결(`shared_media_saved_places`)이 있거나, 분석에 성공한 지우지 않은 내 공유의 게시물에서 추출(`media_places`)된 장소다. 체크는 결정 4대로 연결이 아니라 보관함 레코드로 그리므로, 장소를 뺐다가 다른 게시글로 다시 저장해 연결이 없는 게시글에도 체크로 보이는 장소는 남긴다. 연결만 보면 다시 저장한 게시글을 지울 때 지우지 않은 게시글의 체크가 풀린다.
- 폴더에 담긴 장소도 지운다(11-05 정콩 결정). 규칙이 「해당 게시글에서만 나온 장소는 지운다」 하나로 단순해지고 회의 문장과도 맞는다. 폴더 지정은 같은 게시물을 다시 공유해도 돌아오지 않으므로, 앱이 삭제 확인 창에서 함께 빠질 장소를 알린다.

### 2. 게시글 하나를 지우면 같은 게시물의 내 공유를 모두 지운다

게시물 탭은 게시물마다 가장 최근 공유 한 건만 보여 준다. 대표 공유 한 건만 지우면 예전 공유가 대신 올라와 지운 게시글이 다시 보이므로, 같은 `media_id`의 내 공유를 모두 지운다.

API는 게시물 ID 대신 카드의 공유 ID(`sharedMediaIds`)를 받고, 서버가 공유 ID를 게시물 ID로 바꾼다. 게시물 탭 응답(#535)은 히스토리 카드와 같은 모양이라 `sharedMediaId`만 내리고, 재시도, 제보, 장소 목록, 체크 켜기(#553)도 모두 공유 ID를 받아서 앱이 ID를 한 종류만 다루게 한다. 게시물 ID로 받더라도 `media`는 여러 회원이 함께 쓰는 캐시라서, 잠그기 전에 내 공유가 남은 게시물만 거르는 조회가 똑같이 필요하다.

### 3. `shared_media`는 soft delete, `saved_places`는 실제로 지운다

`shared_media`에 `deleted_at` 컬럼을 더하고(#551, V5) 지운 시각만 적는다.

- 지운 게시글도 히스토리와 최근 공유 줄에는 그대로 보여 주기로 했다(11-05 정콩 결정). 그래서 `shared_media` 데이터가 남아 있어야 한다.
- `shared_media`를 실제로 지우면 제보 데이터가 CASCADE로 함께 지워진다. 실패한 게시물의 제보는 골든셋 보완과 프롬프트 개선에 쓸 수 있어 남긴다(10-25 러키 의견).
- 유저 데이터 리포트는 `shared_media` 한 건을 공유 한 번으로 센다. 데이터를 남겨야 지난 리포트와 같은 숫자가 나온다.
- `saved_places`는 지금의 장소 삭제와 같은 방식으로 실제로 지운다. 지표가 `saved_places`를 쓰지 않고, data migration 보충 실행이 사라진 데이터를 다시 넣지 않는 규칙도 실제 삭제를 전제로 한다.

`deleted_at` 조건은 보관함 쪽 조회에만 붙인다.

| 조회 | 조건 | 까닭 |
|---|---|---|
| 게시물 탭 `GET /api/v1/saved-media` | 지운 공유 제외 | 보관함에서 지운 게시글 |
| 장소 상세 릴스 `GET /api/v1/saved-places/{id}/media`, `GET /api/v1/places/{placeId}/media` | 지운 공유 제외 | 보관함에서 지운 게시글 |
| 추출 완료 뒤 장소를 연결할 공유 찾기 | 지운 공유 제외 | 지운 게시글의 장소가 보관함에 다시 들어오지 않게 |
| 재시도가 이어받을 분석 중인 공유 찾기 | 지운 공유 제외 | 지운 공유를 이어받으면 장소가 붙지 않아서, 재시도가 새 공유를 만들게 |
| 게시글 삭제가 남길 장소 확인 | 지운 공유 제외 | 결정 1의 「다른 게시글에도 있는 장소」 |
| 히스토리 목록과 상세, 재시도할 공유 읽기, 제보 | 조건 없음 | 지운 게시글도 히스토리에 그대로 보여 주고 재시도와 제보를 받는다 |

### 4. 게시물 상세의 장소 체크는 `saved_places` 레코드가 있는지로 그린다

회의에서 장소 삭제 대신 게시물에서 장소를 골라 저장하는 안을 골랐고, 처음 추출하면 모든 장소가 저장된 상태다.

- 체크는 내 `saved_places`에 해당 장소의 레코드가 있는지로 그린다. 게시물 탭 응답이 이미 `savedPlaceId`(없으면 null)를 내려 준다.
- 체크 끄기는 지금의 `DELETE /api/v1/saved-places`를 그대로 쓰고, 체크 켜기는 `POST /api/v1/saved-places`를 새로 만든다(#553).
- 「해제」 표시 컬럼을 따로 두지 않는다. 표시 컬럼을 두면 보관함 목록, 폴더, 지도, 검색처럼 `saved_places`를 읽는 조회마다 조건이 붙지만, 다시 체크할 때 폴더 지정과 `savedPlaceId`가 남는 점 말고는 나아지는 것이 없다.
- 저장은 장소마다 하나라서, 같은 장소가 게시글 A와 B에 함께 나오면 A에서 체크를 풀 때 B에서도 풀린다. 지도에서 사라진 장소가 B에 체크된 채로 남는 어긋남이 없다.

### 5. 장소를 모두 해제한 게시글도 게시물 탭에 남긴다

게시물 탭의 목록 기준을 「보관함 연결이 남은 내 공유」에서 「지우지 않은 내 공유 가운데 분석에 성공했고 추출된 장소가 1곳 이상인 공유」로 바꾼다(#554, 11-05 정콩 결정). 연결 기준을 그대로 쓰면 장소 체크를 모두 풀었을 때 게시글이 탭에서 사라져, 장소를 다시 체크할 곳이 없어진다.

### 6. 장소 상세의 릴스 목록은 장소 id로 추출 결과를 읽는다

`GET /api/v1/places/{placeId}/media`를 새로 만들어, 추출 결과(`media_places`)에 해당 장소가 있는 지우지 않은 내 공유를 돌려준다(#555).

- 지금 목록은 저장할 때 만든 `shared_media_saved_places`를 읽어서, 저장하지 않은 장소는 빈 목록이고, 장소를 지웠다가 다른 게시글로 다시 저장하면 이전 게시글이 빠진다.
- 내 공유 상태가 `SUCCEEDED`인 공유만 넣는다(11-05 정콩 결정). 내 공유는 실패인데 다른 회원의 공유로 같은 게시물 추출이 성공한 경우, 히스토리에서는 실패이고 게시물 탭에는 없는 게시글이 장소 상세에만 나타나기 때문이다.
- 기존 `GET /api/v1/saved-places/{savedPlaceId}/media`는 이미 나간 2.2.x 앱이 쓰므로 남긴다.

### 7. 게시글 삭제는 `media`부터 잠그고, 지울 장소는 유니크 인덱스로 잠근 뒤 남은 게시글에 있는지 따로 확인한다

- 고른 게시물의 `media` 레코드를 ID 순서로 `FOR UPDATE` 잠근 뒤 `shared_media`를 바꾼다. 공유 접수(`ShareService.createShare`)와 추출 완료(`MediaExtractionResultWriter.recordSuccess`)도 `media`를 먼저 잠그므로, 같은 게시물을 두고는 차례로 실행된다. 지우는 사이에 추출이 끝나도 추출 완료가 `media` 잠금을 기다린 뒤 지운 공유를 읽게 되어, 지운 공유에 장소가 붙지 않는다.
- 지울 장소는 네 단계로 고른다. 지운 게시물에서 추출됐거나 지운 게시물의 공유에 연결된 장소 가운데 보관함에 있는 장소 ID를 락 없이 읽고, 읽은 장소의 항목을 `(member_id, place_id)` 유니크 인덱스로 장소 ID 순서대로 `FOR UPDATE` 잠근다. 잠근 뒤 결정 1의 기준으로 남은 게시글에 없는 항목 ID를 일반 SELECT로 읽고, 읽은 ID만 `member_id` 조건과 함께 지운다.
- 후보에 추출된 장소도 넣는 까닭은, 같은 장소가 나오는 게시글 둘을 동시에 지울 때 두 요청이 같은 항목을 잠가 차례로 실행되게 하려는 것이다. 연결된 장소만 후보로 읽으면 연결이 없는 쪽 요청은 장소를 보지 않고 끝나고, 연결이 있는 쪽 요청은 아직 커밋 전인 상대 게시글을 남은 게시글로 보고 장소를 남겨서, 두 게시글을 모두 지웠는데 장소가 남는다.
- 유니크 인덱스로 잠그는 까닭은 공유와 추출 완료의 저장(`INSERT ... ON DUPLICATE KEY UPDATE`)이 같은 인덱스부터 잠그기 때문이다. 기본 키로 잠그면 저장은 유니크 인덱스를 쥔 채 기본 키를 기다리고, 삭제는 기본 키를 쥔 채 유니크 인덱스를 기다린다.
- 남은 게시글 확인을 DELETE 안의 서브쿼리로 하지 않는 까닭은, 서브쿼리가 회원의 다른 공유 레코드에 공유 락을 걸기 때문이다. 같은 장소를 가진 게시글 둘을 동시에 지우거나, 같은 회원의 다른 게시물 추출 완료가 자기 공유 레코드를 고치려 할 때 서로 기다리게 된다.
- 트랜잭션은 READ COMMITTED로 연다(`ShareService.createExtractionRetry`와 같은 방식). 잠금을 기다린 뒤의 일반 SELECT가 그사이 커밋된 연결과 공유 삭제까지 보게 하려는 것이다. 공유 연결을 넣으려면 외래 키 확인으로 보관함 항목 레코드에 공유 락이 필요하므로, 잠근 뒤에는 새 연결이 생기지 않는다.
- 공유와 추출 완료의 저장(`SavedPlaceRegistrationService.savePlacesFromShare`)도 함께 고친다. 장소 ID 오름차순으로 저장해서 삭제와 같은 순서로 잠그고, 저장 뒤 보관함 항목 ID를 다시 읽는 조회(`SavedPlaceDao.getIdByMemberAndPlaceForUpdate`)를 `FOR UPDATE`로 바꾼다. 일반 SELECT로 다시 읽으면 REPEATABLE READ 스냅숏에 남은 지운 항목 ID를 받아서, 게시글 삭제 직후 같은 장소를 다시 저장하는 공유나 추출 완료가 공유 연결 INSERT에서 외래 키(1452)에 걸린다. 두 위험 모두 #274 리뷰에서 드물다고 미뤘는데, 게시글 삭제가 장소를 한꺼번에 지우면서 더 자주 겹치게 된다.
- MySQL 8.4.11에서 두 세션으로 확인했다. DELETE 한 문장(REPEATABLE READ)과 기본 키 잠금 방식은 추출 완료나 다른 게시글 삭제와 겹치면 `ERROR 1213 Deadlock found`를 냈고, 지금 방식은 같은 순서에서 두 트랜잭션이 모두 커밋되었으며 남겨야 할 장소는 남고 지울 장소는 지워졌다. 추출 결과 조건은 잠금 없는 일반 SELECT에만 더해서 잠그는 대상과 순서는 바뀌지 않는다. 삭제 직후 같은 장소를 다시 저장하는 경우는 다시 읽기가 일반 SELECT일 때 외래 키 오류(1452)가 났고, `FOR UPDATE`로 바꾸면 커밋되었다.

## 남은 결정

- **체크를 보내는 시점:** 체크할 때마다 서버에 보내는 것을 기본으로 한다. 지금 앱은 장소 삭제와 폴더 담기에서 서버 응답을 받은 뒤 화면을 바꾸므로, 체크에 낙관적 업데이트를 쓸지는 FE가 정한다.
- **지운 게시글 되살리기:** 되살리는 API는 만들지 않고, 같은 게시물을 다시 공유하면 새 게시글로 장소가 다시 담긴다. 폴더 지정은 돌아오지 않는다.
- **다시 저장한 장소의 연결:** 체크를 다시 켜면 `shared_media_saved_places` 연결은 지금 게시글 하나에만 생긴다. 게시글 삭제는 결정 1대로 추출 결과도 보고 장소 상세 목록은 결정 6대로 추출 결과로 읽으므로, 연결이 하나뿐이어도 화면은 어긋나지 않는다. 연결을 다시 쓰는 곳이 생기면 그때 정한다.
- **검색:** #532 게시글 검색도 결정 5의 기준과 지운 공유 조건을 따라야 한다(#532 코멘트로 공유함).
- **data migration:** #551이 운영에 배포된 뒤, 실패 게시물 batch SQL이 지운 공유에 장소를 넣지 않도록 `deleted_at` 조건을 더한다(data migration 쪽에서 처리).
