## 결정 요약

앱과 서버가 서로의 배포를 막지 않도록 분야마다 상시 개발 브랜치와 출시 브랜치를 따로 둔다. `main`은 실제로 나간 것의 스냅샷으로만 쓴다.

## 맥락과 문제

[인프라 ADR-04](adr-04-monorepo-branch.md)는 상시 브랜치를 `main`과 `develop` 둘로 뒀다. release와 hotfix는 앱 출시에만 쓰고 서버는 `develop`에서 `main`으로 바로 머지해 배포하기로 했다. 그 결정은 서버가 머지 즉시 배포되고 되돌리기 쉽다는 전제에 서 있었다.

그 전제가 깨졌다.

- 서버가 개발 서버와 운영 서버로 나뉘었다. `develop` 하나로는 어느 쪽으로 가는 변경인지 구분할 수 없다.
- 운영 배포에 승인 관문과 헬스 판정, 롤백이 붙었다(ADR-02). 이제는 머지해도 즉시 배포되지 않고 검증을 거친다.
- 프론트는 이미 `fe-release/1.0.0`, `1.0.1`, `1.1.0`으로 출시해 왔다. ADR-04가 정한 `release/x.y.z` 이름과 어긋난다.
- `develop` 하나에 앱과 서버가 섞이면 브랜치 보호 규칙도 하나만 걸린다. 경로 필터로 CI는 갈라도 서버 필수 체크가 앱 PR에까지 따라붙는다.

## 결정 기준

1. 앱 출시 준비가 서버 배포를 멈추지 않아야 하고 그 반대도 같아야 한다.
2. 브랜치 이름만 보고 어느 서버로 가는 변경인지 알 수 있어야 한다.
3. 필수 체크를 분야별로 다르게 걸 수 있어야 한다.
4. `main`을 보면 무엇이 나가 있는지 알 수 있어야 한다.

## 결정

### 브랜치 구조

| 브랜치 | 역할 | 배포 |
| --- | --- | --- |
| `main` | 실제로 나간 것의 스냅샷 | 배포하지 않는다 |
| `be-dev` | 서버 상시 개발 | 머지하면 개발 서버로 배포 |
| `be-release` | 서버 출시 | 머지하면 운영 서버로 배포 |
| `fe-dev` | 클라이언트 상시 개발 | 배포하지 않는다 |
| `fe-release/x.y.z` | 앱 출시 준비 | 스토어 제출 |
| `feat/#번호` 등 | 작업 브랜치 | 해당 분야 dev에서 분기 |

`main`은 배포 대상이 아니라 무엇이 나갔는지 확인하고 태그를 다는 자리다. 서버 출시 태그는 `backend-v1.0.0` 형식으로 붙인다.

### 흐름

```
feat/#번호  ──PR──▶  be-dev  ──머지──▶  개발 서버 배포
                       │
                       └──PR──▶  be-release  ──머지──▶  운영 서버 배포
                                      │
                                      └──PR──▶  main  ──태그──▶  backend-v1.0.0

feat/#번호  ──PR──▶  fe-dev  ──분기──▶  fe-release/x.y.z  ──▶  스토어 제출
                                             │
                                             └──PR──▶  main
```

### main 진입 규칙

`main`으로 들어오는 PR은 `be-release`와 `fe-release/*`에서만 허용한다. 다른 브랜치에서 온 PR은 `.github/workflows/require-develop-for-main.yml`이 `github.head_ref`를 보고 막는다.

워크플로 파일명과 Job 이름에는 `develop`이라는 낱말이 남아 있다. GitHub 필수 체크 설정이 그 이름을 잡고 있어서 그대로 뒀다. 필수 체크를 다시 걸 때 같이 바꾼다.

### CI와 CD 트리거

- `backend-ci.yml`은 `be-dev`로 오는 PR에서만 돈다. 대상 경로는 `Backend/**`와 워크플로 파일이다.
- `backend-cd.yml`은 `be-release`로 오는 PR에서는 검증만 한다. `be-dev`와 `be-release` push에서는 검증, 발행, 배포를 한다. 배포 잡은 `github.event_name == 'push'`일 때만 돈다.
- 배포 대상은 `github.ref_name`이 정한다. `be-release`면 운영 러너와 `prod` 프로필, 그 밖이면 개발 러너와 `dev` 프로필이다.

**CI는 PR만 맡고 머지 뒤 검증은 CD의 `verify` 잡이 맡는다.** 둘 다 `be-dev` push에 반응하면 머지 한 번에 같은 테스트가 두 번 돈다.

PR 중의 검증은 줄지 않는다. `pull_request` 트리거가 `synchronize`에도 반응하므로 PR에 커밋을 올릴 때마다 CI가 돈다. `concurrency`의 `cancel-in-progress: true`가 걸려 있어 연달아 푸시하면 앞 실행이 취소되고 마지막 것만 끝까지 간다.

머지 뒤 검증을 CD에 맡겨도 되는 이유는 `pull_request` 이벤트가 PR 브랜치가 아니라 base와 합친 결과를 검사하기 때문이다. 다만 PR CI가 돈 뒤에 `be-dev`가 움직이면 검사한 것과 실제 머지 결과가 달라지는데, CD의 `verify`가 그 틈을 막는다.

fork PR에는 시크릿이 주입되지 않는다. 배포 잡을 push에서만 돌게 한 덕분에 fork PR은 `verify` 잡까지만 가고 시크릿이 필요하지 않다.

### `be-release` 승격

`be-release`에 push된 커밋으로 이미지를 새로 빌드하지 않는다. `be-dev`에서 이미 빌드하고 개발 서버에서 돌려 본 이미지를 그대로 배포한다. ADR-01의 Build Once, Promote를 지키려는 것이다.

머지하면 커밋 SHA가 달라지므로 `be-dev`에서 만든 이미지를 SHA로는 찾지 못한다. 대신 머지 커밋의 부모를 읽어서 찾는다.

```
                        이미지 :C          이미지 :D
                             │                 │
be-dev       A ──── B ──── C ──── D
                                    ╲
                                     ╲  Merge Commit
                                      ╲
be-release   X ──── Y ────────────────── M
                                         부모1 = Y (be-release의 직전 끝)
                                         부모2 = D (be-dev에서 넘어온 것)
```

판정은 이 순서로 한다.

1. M의 두 번째 부모 P가 있고 P가 `be-dev`의 조상이면(`git merge-base --is-ancestor P origin/be-dev`) `:P` 이미지를 승격한다. 빌드하지 않는다.
2. 아니면 hotfix 경로인지 본다. M에 연결된 PR의 head 브랜치가 `hotfix/`로 시작하고 PR에 `hotfix` 라벨이 붙었으면 새로 빌드해서 배포한다.
3. 둘 다 아니면 배포를 거부한다.

부모 수를 먼저 보지 않고 조상 관계를 먼저 보는 이유는, hotfix를 머지 커밋으로 넣으면 부모가 둘이지만 두 번째 부모가 `be-dev`의 조상이 아니기 때문이다. 부모 수로 먼저 가르면 그 경우가 1번에 빠져 거부된다.

### 머지 방식

**`be-dev`에서 `be-release`로 넘길 때는 Merge Commit으로 한다.** squash로 넘기면 부모가 하나가 되어 승격 대상을 찾을 수 없고, 위 판정의 3번에 걸려 배포가 거부된다.

GitHub ruleset의 `allowed_merge_methods`로 강제한다. `be-release`를 대상으로 `Merge`만 남기고 `Squash`와 `Rebase`를 끈다. 작업 브랜치에서 `be-dev`로 들어올 때는 제한하지 않는다.

### hotfix 경로

운영에 급한 수정이 필요하면 `be-release`에서 `hotfix/#번호`로 분기해 `be-release`로 되돌린다. `be-dev`를 거치지 않는다. 거치면 개발 중인 다른 변경까지 운영에 딸려 나간다.

PR에 `hotfix` 라벨을 붙인다. 라벨이 없으면 승격 판정의 3번에 걸려 배포가 거부된다. 브랜치 이름과 라벨을 둘 다 보는 이유는 하나만으로는 실수로 열리기 때문이다. 이름만 보면 `hotfix/`로 시작하는 아무 브랜치나 운영에 올릴 수 있고, 라벨만 보면 라벨을 잘못 붙인 PR이 그렇게 된다.

hotfix로 나간 것은 뒤이어 `be-dev`에도 반영한다. 안 하면 다음 승격 때 되돌아간다.

## 검토한 선택지

### 선택지 A: ADR-04 유지 (`develop` 하나)

**단점.** 개발 서버와 운영 서버를 구분할 자리가 없다. 브랜치 보호를 분야별로 나눌 수 없다. 프론트가 이미 쓰는 `fe-release/*`와 이름이 어긋난다.

**결론: 채택하지 않는다.**

### 선택지 B: 분야별 트렁크와 출시 브랜치 (채택)

**장점.** 앱과 서버가 서로의 출시 준비에 묶이지 않는다. 브랜치 이름이 곧 배포 대상이다. 필수 체크를 분야별로 다르게 걸 수 있다. 프론트의 기존 운영 방식을 그대로 흡수한다.

**단점.** 상시 브랜치가 둘이라 `main`과 벌어진 간격을 둘 다 관리해야 한다. 한 PR이 앱과 서버를 함께 고치면 두 갈래로 나눠 올려야 한다.

### 선택지 C: 저장소를 앱과 서버로 쪼갠다

**장점.** 브랜치 규칙이 각 저장소 안에서 단순해진다.

**단점.** 이번 스프린트 안에 저장소를 쪼갤 시간이 없다. 이슈와 PR 이력이 갈라진다. 우테코가 준 저장소 하나를 쓰는 전제와 맞지 않는다.

**결론: 채택하지 않는다.**

## 결과

### 좋아지는 것

- 앱 출시 준비 중에도 서버를 배포할 수 있다.
- 개발 서버 배포와 운영 서버 배포가 브랜치로 갈려 사고 범위가 좁아진다.
- 필수 체크를 `be-release`에만 강하게 걸 수 있다.

### 감수하는 것

- 상시 브랜치가 둘이라 `main`이 뒤처지기 쉽다. 출시할 때마다 `main`으로 올려야 하고 한 번이라도 빠뜨리면 `main`은 더 이상 스냅샷이 아니다.
- 앱과 서버를 함께 고치는 변경은 PR을 둘로 나눠야 한다. `require-develop-for-main.yml`처럼 양쪽에 걸리는 파일은 한쪽 PR에만 실린다. 그래서 이런 파일을 고칠 때는 다른 쪽에 미리 알려야 한다.

## 남은 결정

- **`be-dev`의 필수 체크.** `be-release`는 Merge Commit 강제와 승인 한 건으로 정했지만, `be-dev`에 어떤 필수 체크와 승인 수를 걸지는 정하지 않았다. `Require branches to be up to date before merging`을 걸면 PR CI가 검사한 머지 결과와 실제 머지 결과가 어긋나는 틈이 좁아진다.
- **`require-develop-for-main.yml`의 이름.** 파일명과 Job 이름에 `develop`이 남아 있다. 필수 체크 설정이 그 이름을 잡고 있어 같이 바꿔야 한다.
- **`main` 태그 규칙.** 서버 태그는 `backend-v1.0.0`으로 정했지만 앱 태그와 어떻게 맞출지는 정하지 않았다.

## 갱신 기록

- **2026-09-29.** 「남은 결정」에 있던 세 항목을 채웠다.
  - **`be-release` 승격 방식.** 머지 커밋의 두 번째 부모를 승격 대상으로 잡고 `be-dev`의 조상인지 확인한 뒤 재빌드 없이 배포한다. 같은 코드를 테스트 5번 컴파일 7번 돌리던 것이 테스트 3번 컴파일 3번으로 줄고, 운영에 나가는 이미지가 개발에서 검증한 그 이미지가 된다.
  - **머지 방식.** 승격이 부모 관계에 기대므로 `be-dev`에서 `be-release`로는 Merge Commit으로 넘긴다. ruleset의 `allowed_merge_methods`로 강제한다.
  - **서버 hotfix 경로.** `be-release`에서 분기해 `be-release`로 되돌린다. 브랜치 이름과 `hotfix` 라벨을 둘 다 확인한 경우에만 새로 빌드한다.
  - 같은 날 `backend-ci.yml`의 push 트리거를 떼어 CI는 PR만, CD는 머지 뒤를 맡게 나눴다.
  - 승격 판정은 결정만 기록했고 `backend-cd.yml`에는 아직 구현하지 않았다. 구현 상태는 [current-state.md](current-state.md)를 본다.

## 재검토 조건

- 저장소를 앱과 서버로 쪼개게 된다.
- 서버에 스테이징 환경이 추가된다.
- 팀 인원이 늘어 상시 브랜치 하나로 통합 속도를 감당하지 못한다.
- 앱과 서버를 함께 출시해야 하는 요구가 생긴다.

결정을 변경할 때는 이 문서를 덮어쓰지 않는다. 새 ADR을 작성하고 이 문서의 상태를 Superseded로 바꾼다.
