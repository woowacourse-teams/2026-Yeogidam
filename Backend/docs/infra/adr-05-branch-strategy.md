# 인프라 ADR-05. 분야별 트렁크와 출시 브랜치 전략

| | |
| --- | --- |
| Status | Accepted |
| Area | Infrastructure |
| Category | Git, CI/CD |
| Date | 2026-09-28 |
| Supersedes | [인프라 ADR-04 모노레포 브랜치 전략](adr-04-monorepo-branch.md) |

## 결정 요약

우리는 앱과 서버가 서로의 배포를 막지 않도록, 분야마다 상시 개발 브랜치와 출시 브랜치를 따로 두고 `main`은 실제로 나간 것의 스냅샷으로만 쓴다.

## 맥락과 문제

[인프라 ADR-04](adr-04-monorepo-branch.md)는 상시 브랜치를 `main`과 `develop` 둘로 두고, release와 hotfix를 앱 출시에만 쓰며, 서버는 `develop`에서 `main`으로 바로 머지해 배포하기로 했다. 그 결정이 서 있던 전제는 서버가 머지 즉시 배포되고 되돌리기 쉽다는 것이었다.

그 전제가 깨졌다.

- 서버에 개발 서버와 운영 서버가 생겼다. `develop` 하나로는 어느 서버로 가는 변경인지 구분할 수 없다.
- 운영 배포에 승인 관문과 헬스 판정과 롤백이 붙었다(ADR-02). 즉시 배포가 아니라 검증을 거치는 배포가 됐다.
- 프론트는 이미 `fe-release/1.0.0`, `1.0.1`, `1.1.0`으로 출시해 왔다. ADR-04가 정한 `release/x.y.z` 이름을 따르지 않는다.
- `develop` 하나에 앱과 서버가 섞이면 경로 필터로 CI를 갈라도 브랜치 보호 규칙은 하나만 걸린다. 서버 필수 체크를 앱 PR에도 요구하게 된다.

## 결정 기준

1. 앱 출시 준비가 서버 배포를 멈추지 않아야 하고, 그 반대도 같아야 한다.
2. 브랜치 이름만 보고 어느 서버로 가는 변경인지 알 수 있어야 한다.
3. 필수 체크를 분야별로 다르게 걸 수 있어야 한다.
4. `main`을 보면 지금 나가 있는 것이 무엇인지 알 수 있어야 한다.

## 결정

### 브랜치 구조

| 브랜치 | 역할 | 배포 |
| --- | --- | --- |
| `main` | 실제로 나간 것의 스냅샷 | 배포하지 않는다 |
| `be-dev` | 서버 상시 개발 | 머지하면 개발 서버로 배포 |
| `be-release` | 서버 출시 | 머지하면 운영 서버로 배포 |
| `fe-dev` | 클라이언트 상시 개발 | 배포하지 않는다 |
| `fe-release/x.y.z` | 앱 출시 준비 | 스토어 제출 |
| `feat/#번호` 등 | 작업 브랜치 | 해당 분야 dev에서 분기 |

`main`은 배포 대상이 아니다. 무엇이 나갔는지 확인하고 태그를 다는 자리다. 서버 출시 태그는 `backend-v1.0.0` 형식으로 붙인다.

### 흐름

```
feat/#번호  ──PR──▶  be-dev  ──머지──▶  개발 서버 배포
                       │
                       └──PR──▶  be-release  ──머지──▶  운영 서버 배포
                                      │
                                      └──PR──▶  main  ──태그──▶  backend-v1.0.0

feat/#번호  ──PR──▶  fe-dev  ──분기──▶  fe-release/x.y.z  ──▶  스토어 제출
                                             │
                                             └──PR──▶  main
```

### main 진입 규칙

`main`으로 들어오는 PR은 `be-release`와 `fe-release/*`에서만 허용한다. `.github/workflows/require-develop-for-main.yml`이 `github.head_ref`를 보고 막는다.

워크플로 파일명과 Job 이름에 `develop`이라는 낱말이 남아 있는데, GitHub 필수 체크 설정이 그 이름을 잡고 있어서 그대로 뒀다. 필수 체크를 다시 걸 때 같이 바꾼다.

### CI와 CD 트리거

- `backend-ci.yml`은 `be-dev`로 오는 PR과 `be-dev` push에서 돈다. 경로는 `Backend/**`와 워크플로 파일이다.
- `backend-cd.yml`은 `be-release`로 오는 PR에서는 검증만 하고, `be-dev`와 `be-release` push에서 검증과 발행과 배포를 한다. 배포 잡은 `github.event_name == 'push'`일 때만 돈다.
- 배포 대상은 `github.ref_name`이 정한다. `be-release`면 운영 러너와 `prod` 프로필, 그 밖이면 개발 러너와 `dev` 프로필이다.

fork PR에는 시크릿이 주입되지 않는다. 배포 잡을 push에서만 돌게 한 덕분에 fork PR은 `verify` 잡까지만 가고 시크릿을 필요로 하지 않는다.

## 검토한 선택지

### 선택지 A: ADR-04 유지 (`develop` 하나)

**단점.** 개발 서버와 운영 서버를 구분할 자리가 없다. 브랜치 보호를 분야별로 나눌 수 없다. 프론트가 이미 쓰는 `fe-release/*`와 이름이 어긋난다.

**결론: 채택하지 않는다.**

### 선택지 B: 분야별 트렁크와 출시 브랜치 (채택)

**장점.** 앱과 서버가 서로의 출시 준비에 묶이지 않는다. 브랜치 이름이 곧 배포 대상이다. 필수 체크를 분야별로 다르게 걸 수 있다. 프론트의 기존 운영 방식을 그대로 흡수한다.

**단점.** 상시 브랜치가 둘이라 `main`과의 간격을 둘 다 관리해야 한다. 한 PR이 앱과 서버를 함께 고치면 두 갈래로 나눠 올려야 한다.

### 선택지 C: 저장소를 앱과 서버로 쪼갠다

**장점.** 브랜치 규칙이 각 저장소 안에서 단순해진다.

**단점.** 이번 스프린트 안에 저장소를 쪼갤 시간이 없다. 이슈와 PR 이력이 갈라진다. 우테코가 준 저장소 하나를 쓰는 전제와 맞지 않는다.

**결론: 채택하지 않는다.**

## 결과

### 좋아지는 것

- 앱 출시 준비 중에도 서버를 배포할 수 있다.
- 개발 서버 배포와 운영 서버 배포가 브랜치로 갈려 사고 범위가 좁아진다.
- 필수 체크를 `be-release`에만 강하게 걸 수 있다.

### 감수하는 것

- 상시 브랜치가 둘이라 `main`이 뒤처지기 쉽다. 출시 때마다 `main`으로 올리는 절차를 빠뜨리면 스냅샷이 아니게 된다.
- 앱과 서버를 함께 고치는 변경은 PR을 둘로 나눠야 한다. 예를 들어 `require-develop-for-main.yml`처럼 양쪽에 걸리는 파일은 한쪽 PR에 실리므로 다른 쪽에 미리 알려야 한다.

## 남은 결정

- **`be-release` 승격 방식.** 지금은 `be-release` push가 이미지를 다시 빌드한다. 머지하면 커밋 SHA가 달라져 `be-dev`에서 만든 이미지를 찾지 못하기 때문이다. ADR-01의 Build Once, Promote를 지키려면 승격 판정이 필요하다. 별도 ADR로 다룬다.
- **브랜치 보호 규칙.** `be-dev`와 `be-release`에 어떤 필수 체크와 승인 수를 걸지 정해야 한다. 현재 필수 체크 이름이 `Require develop source branch`로 잡혀 있다.
- **서버 hotfix 경로.** 운영에 급한 수정이 필요할 때 `be-release`에서 바로 분기할지, `be-dev`를 거칠지 정하지 않았다.
- **`main` 태그 규칙.** 서버는 `backend-v1.0.0`으로 정했지만 앱 태그와의 관계를 정하지 않았다.

## 재검토 조건

- 저장소를 앱과 서버로 쪼개게 된다.
- 서버에 스테이징 환경이 추가된다.
- 팀 인원이 늘어 상시 브랜치 하나로 통합 속도를 감당하지 못한다.
- 앱과 서버를 함께 출시해야 하는 요구가 생긴다.

결정을 변경할 때는 이 문서를 덮어쓰지 않는다. 새 ADR을 작성하고 이 문서의 상태를 Superseded로 바꾼다.
