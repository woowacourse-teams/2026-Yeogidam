> **이 결정은 더 이상 쓰지 않는다.** 서버에 자체 출시 경로(`be-release`)가 생기면서 「서버는 release와 hotfix를 쓰지 않는다」는 결정이 무너졌다. 대신할 문서는 [인프라 ADR-05 분야별 트렁크와 출시 브랜치 전략](adr-05-branch-strategy.md)이다. 아래 본문은 왜 처음에 이렇게 정했는지를 남기려고 그대로 둔다.
>
> | | 이 문서 | 현재 원격 |
> | --- | --- | --- |
> | 상시 브랜치 | `main`, `develop` 하나 | `main`, `be-dev`, `fe-dev` |
> | 출시 브랜치 | `release/x.y.z` (앱 전용) | `be-release`, `fe-release/1.0.0`, `1.0.1`, `1.1.0` |
> | 서버 배포 | `develop`에서 `main`으로 머지 | `be-dev` 머지로 개발 배포, `be-release` 머지로 운영 배포 |
> | main 진입 규칙 | 문서에 없음 | `require-develop-for-main.yml`이 `be-release`와 `fe-release/*`만 허용 |

## 결정 요약

우리는 배포 주기가 다른 앱과 서버를 한 저장소에서 관리하기 위해, 앱에만 release와 hotfix를 적용하는 변형 git-flow를 채택한다.

**용어 정리.** 표준 git-flow는 브랜치를 main, develop, feature, release, hotfix 다섯 종류로 두고, 저장소의 모든 코드에 이 규칙을 똑같이 적용한다. 표준대로라면 main으로 들어가는 모든 변경은 반드시 release나 hotfix를 통과해야 하므로, 서버 코드를 한 줄 고쳐도 release 브랜치에 실려 나가야 한다. 이 문서는 브랜치 다섯 종류를 그대로 쓰되, release와 hotfix의 적용 범위를 앱으로 좁히자고 제안한다. 표준 규칙 그대로도 아니고, develop과 release가 있으니 GitHub flow도 아니다. git-flow를 기반으로 일부 규칙을 바꿨다는 뜻에서 변형 git-flow라고 부른다. 공식 용어는 아니고 설명하려고 붙인 이름이다.

## 맥락과 문제

여기담 저장소는 모노레포로, 안드로이드 앱(React Native)과 서버 코드를 한곳에 담아 관리한다. 두 배포물은 배포 방식이 다르다. 앱은 스토어 심사를 거쳐 버전 단위로 출시되고 한번 나간 버전은 되돌릴 수 없다. 서버는 심사 없이 머지 즉시 배포되고 문제가 생기면 바로 되돌릴 수 있다.

현재 브랜치는 main, develop, fe-develop과 릴리즈용 1.0.0, 1.0.1이 섞여 있다. 브랜치별 역할은 문서로 정해두지 않았다. PR은 팀 저장소 안의 작업 브랜치에서 develop 계열로 보내는 흐름이 자리 잡았다. CI/CD 워크플로우 구축 PR(#75)은 진행 중이다.

프로젝트 공식 일정이 9월 4일까지라 규칙을 지키는 비용이 배포 횟수보다 커지면 안 된다. CI/CD가 브랜치 구조를 전제로 만들어지므로 지금 결정해야 한다.

## 결정 기준

### 필수 조건

- 앱 출시 QA 기간에도 develop에서 다음 개발을 이어갈 수 있어야 한다.
- 서버 수정은 릴리즈 일정과 무관하게 즉시 배포할 수 있어야 한다.
- 다섯 명이 남은 기간 안에 규칙을 지킬 수 있을 만큼 단순해야 한다.

### 선호 조건

- 지금까지의 PR 리뷰 흐름을 바꾸지 않는다.
- 경로 기반 CI(앱 폴더 변경은 앱 빌드만, 서버 폴더 변경은 서버 배포만)와 자연스럽게 맞물린다.

## 검토한 선택지

### 선택지 A: 표준 git-flow 전체 적용

**설명.** master, develop, feature, release, hotfix를 앱과 서버 구분 없이 저장소 전체에 적용한다.

**장점**

- 널리 알려진 표준이라 참고 자료가 많다.
- 앱 출시 준비와 긴급 수정 절차가 명확해진다.

**단점**

- release 브랜치를 끊는 순간 앱과 무관한 서버 변경까지 함께 얼어붙는다.
- 몇 분이면 나갈 수 있는 서버 긴급 수정도 hotfix 절차를 거쳐 배포가 느려진다.
- 저장소 전체에 하나의 버전 태그를 달아서 태그의 의미가 모호해진다.

**확인한 것.** 참고한 우아한형제들 기술 블로그 글도 완벽한 규칙보다 팀 상황에 맞게 유연하게 적용하라고 권한다.

### 선택지 B: GitHub flow

**설명.** main과 feature 브랜치만 두고 main 머지가 곧 배포인 단순한 흐름을 쓴다.

**장점**

- 규칙이 가장 단순해서 지키는 비용이 거의 없다.
- 즉시 배포되는 서버와는 잘 맞는다.

**단점.** 앱 출시 QA 기간을 담을 자리가 없어 QA 중에는 main 머지를 멈추거나 미완성 기능이 스토어 버전에 섞여 들어간다.

### 선택지 C: 변형 git-flow (앱에만 release와 hotfix 적용)

**설명.** main과 develop을 상시 유지하고 feature는 develop에서 분기한다. release와 hotfix 브랜치는 앱 출시에만 사용하고 서버는 develop에서 main으로 흐르는 단순한 경로로 배포한다.

**장점**

- 앱은 QA 기간을 확보하고 서버는 즉시 배포를 유지한다.
- 기존 1.0.0, 1.0.1 브랜치 운영 방식은 이름과 규칙만 정리하면 되니 도입 비용이 낮다.

**단점.** 브랜치 규칙이 앱과 서버에서 달라 문서 없이는 헷갈릴 수 있다.

**확인한 것.** 현재 열린 PR과 브랜치 구조에서 추가로 옮기거나 지워야 할 브랜치는 fe-develop뿐이다.

## 결정

우리는 변형 git-flow(선택지 C)를 채택한다.

- `main`은 실제 배포된 상태를 가리킨다. 앱 출시 시 `v1.2.0` 형식의 태그를 단다. 태그는 앱 출시에만 사용한다.
- `develop`은 하나만 관리한다. `fe-develop`은 `develop`으로 합치고 삭제한다.
- feature 브랜치는 `develop`에서 분기하고 PR 리뷰를 거쳐 `develop`으로 돌아온다.
- `release/x.y.z`는 앱 출시 준비에만 `develop`에서 분기한다. QA 수정 후 `main`과 `develop` 양쪽에 머지하고 삭제한다.
- hotfix는 앱 긴급 수정에만 `main`에서 분기한다. 수정 후 `main`과 `develop` 양쪽에 머지한다.
- 서버 수정은 `develop`에서 `main`으로 머지해 바로 배포한다. release와 hotfix를 쓰지 않는다.
- CI는 경로 필터로 앱과 서버를 분리해 실행한다.

앱 작업이든 서버 작업이든 몸통은 같다. main과 develop이라는 상시 브랜치 두 개가 있고, feature는 develop에서 분기해 PR 리뷰를 거쳐 develop으로 돌아온다. 갈라지는 곳은 develop에서 main으로 넘어가는 길뿐이다. 모든 작업은 develop에 모여 main으로 나가고 앱만 나가는 길목에 release라는 대기실이 하나 더 있다.

**이 선택을 한 이유**

- 세 선택지 가운데 앱의 QA 기간 확보와 서버의 즉시 배포라는 두 필수 조건을 동시에 만족한다.
- 이미 릴리즈 브랜치를 운영해 본 팀이라 새로 배울 규칙이 가장 적다.

**선택하지 않은 방식과 미채택 이유**

- **선택지 A.** 서버 배포를 앱 릴리즈 일정에 묶어 즉시 배포라는 장점을 잃는다.
- **선택지 B.** 앱 출시 QA 기간을 담을 브랜치가 없다.

## 결과

### 좋아지는 것

- 앱 출시 준비 중에도 다음 스프린트 개발이 멈추지 않는다.
- 브랜치 이름만 보고 어디로 배포되는 변경인지 알 수 있다.

### 감수하는 것

- 앱과 서버의 규칙이 달라 문서를 유지해야 한다.
- release 브랜치의 수정을 main과 develop 양쪽에 머지하는 절차를 빠뜨리면 이력이 어긋난다.

### 가역성

브랜치 전략은 코드에 흔적을 남기지 않으므로 되돌리기 쉽다. 규칙 문서를 바꾸고 다음 릴리즈부터 새 방식을 적용하면 된다.

- 태그와 앱 versionCode 연동 규칙

## 재검토 조건

다음 상황이 생기면 이 결정을 다시 검토한다.

- 서버도 버전을 묶어 출시하는 방식으로 바뀜
- 팀 인원이 늘어 develop 하나로 통합 속도를 감당하지 못함
- 앱 출시 주기가 짧아져 release 브랜치가 상시로 존재하게 됨

결정을 변경할 때는 이 문서를 덮어쓰지 않는다. 새 ADR을 작성하고 이 문서의 상태를 Superseded로 바꾼다.
