## 결정 요약

우리는 운영 서버 비용을 줄이고 CI가 빌드한 이미지를 수정 없이 실행하려고 ARM 아키텍처의 t4g.small 인스턴스를 채택한다.

## 맥락과 문제

여기담 백엔드를 배포할 EC2 인스턴스를 새로 만들어야 한다. ADR-01에서 도커 이미지는 GitHub Actions가 한 번만 빌드하고 그 결과물 하나를 모든 환경에서 쓰기로 정했다. 도커 이미지는 빌드된 CPU 명령어 체계(x86 또는 ARM)에서만 실행되니, 서버의 CPU 아키텍처를 정하는 일이 곧 CI가 어떤 이미지를 빌드할지 정하는 일이 된다. 아키텍처가 어긋난 이미지를 배포하면 빌드와 push까지는 성공한다. 실행하는 순간에야 `exec format error`가 나면서 컨테이너가 뜨지 못한다. 그래서 서버를 만들기 전에 아키텍처를 결정으로 고정해야 한다.

- **현재 상황.** 서울 리전(ap-northeast-2)에는 운영용 인스턴스가 아직 없어서 이번에 처음 만든다. CI는 GitHub Actions를 쓰는데 기본 러너가 x86이다.
- **해결해야 하는 문제.** CI가 빌드한 이미지가 서버에서 그대로 실행되도록 아키텍처와 인스턴스 크기를 정해야 한다.
- **기술적 제약.** 스프링 부트 애플리케이션과 도커를 한 인스턴스에서 함께 돌린다. 스프링 부트는 JVM을 포함해 보통 400~600MB의 메모리를 쓴다. 운영체제와 도커 데몬 몫까지 빼면 1GB 인스턴스에서는 배포 시점에 메모리가 모자라 프로세스가 강제 종료될 수 있다.
- **운영상 제약.** 팀 리포지토리는 공개 상태다. GitHub Actions의 ARM 네이티브 러너는 공개 리포지토리에서 무료이고 비공개 리포지토리에서는 유료다.
- **권한 제약.** 우테코가 관리하는 계정이라 보안 그룹을 새로 만들거나 리소스를 삭제할 권한이 없다. 네트워크도 지정된 VPC(TECHCOURSE-PROJECT)와 용도별 서브넷(직접 접근 EC2는 project-public-a, b), 제공된 보안 그룹(project-public)을 써야 한다. EC2 유형은 t4g.medium 이하만 허용된다. 모든 리소스에 지정 태그 3종(Service, Role, ProjectTeam)이 없으면 운영진이 삭제한다(2026-08-26 확인).
- **비용 제약.** 이 계정은 프리 티어 대상이 아니어서 어떤 유형을 골라도 사용한 만큼 요금이 나간다. 서울 리전 시간당 요금은 t3.small이 0.026달러, t4g.small이 0.0208달러로 t4g가 20퍼센트 싸다(2026-08-26 확인). 팀 월 예산은 8월 50달러, 9월 60달러, 10월부터 70달러다. 예산을 넘기면 리소스가 종료될 수 있다.
- **이 결정을 지금 내려야 하는 이유.** 인스턴스를 만드는 화면에서 아키텍처를 먼저 골라야 한다. 만든 뒤에 아키텍처를 바꾸려면 인스턴스를 새로 만들고 이미지도 다시 빌드해야 한다.

## 결정 기준

1. CI가 빌드한 이미지가 서버에서 추가 조치 없이 실행되어야 한다(ADR-01의 Build Once, Promote 전제 유지).
2. 스프링 부트와 도커를 함께 돌릴 때 배포 시점에도 프로세스가 강제 종료되지 않아야 한다.
3. 월 비용이 낮아야 한다.
4. 전환과 운영에 드는 팀의 학습 부담이 작아야 한다.

### 필수 조건

- CI 빌드 이미지와 서버의 CPU 아키텍처가 일치해야 한다.
- 메모리가 2GB 이상이거나, 1GB라면 스왑으로 보완해야 한다.
- 서울 리전에서 생성한다.
- 계정 정책을 지켜야 한다. EC2 유형은 t4g.medium 이하이고, 지정 VPC와 서브넷, 보안 그룹, 태그 3종이 필수다.

### 선호 조건

- 같은 조건이면 시간당 요금이 싼 쪽을 고른다.
- CI 워크플로 수정 범위가 작아야 한다.

## 검토한 선택지

### 선택지 A: x86 아키텍처, t3.small

**설명.** 인텔 CPU를 쓰는 x86 인스턴스다. GitHub Actions의 기본 러너(`ubuntu-latest`)가 x86이므로 CI를 손대지 않아도 이미지와 서버의 아키텍처가 맞는다.

**장점**

- CI 워크플로를 수정할 필요가 없다.
- 배포 관련 블로그와 강의 자료 대부분이 x86을 전제로 하므로, 팀원이 자료를 따라 하다 환경이 어긋날 일이 없다.

**단점**

- 같은 크기의 t4g보다 시간당 요금이 20퍼센트 비싸다.
- 계정 정책이 EC2 유형을 t4g.medium 이하로 제한하므로 현재 계정에서는 아예 고를 수 없다(2026-08-26 확인).

**확인할 사항.** 계정 정책의 허용 유형이 바뀌어 x86 계열이 열리는지 지켜본다.

### 선택지 B: ARM 아키텍처, t4g.small

**설명.** AWS가 직접 설계한 Graviton CPU를 쓰는 ARM 인스턴스다. CI 워크플로의 실행 환경을 GitHub이 제공하는 ARM 네이티브 러너(`ubuntu-24.04-arm`)로 바꾸면 에뮬레이션 없이 ARM용 이미지를 빌드한다. 빌드 속도도 떨어지지 않고 기존 구조를 그대로 유지한다.

**장점**

- 같은 크기의 t3보다 시간당 요금이 20퍼센트 싸고 성능은 t3에 뒤지지 않는다.
- CI 수정이 `runs-on` 한 줄 교체로 끝나고 공개 리포지토리라 ARM 러너 비용이 없다.

**단점**

- 팀 전원이 우리 이미지가 ARM용이라는 사실을 알고 있어야 한다. x86을 전제로 한 자료를 따라 하다 어긋나면 원인을 아키텍처에서 찾아야 한다.
- 리포지토리가 비공개로 바뀌면 ARM 러너가 유료가 되어 절감분이 상쇄될 수 있다.

**확인할 사항**

- ARM 러너 무료 조건인 리포지토리 공개 여부: 공개 확인(2026-08-26).
- 프리 티어 여부: 대상 아님 확인(2026-08-26). 프리 티어 대상이면 무료인 x86 t3.micro가 있어 결론이 뒤집힌다.
- 기계어 코드를 품은 자바 라이브러리(네이티브 라이브러리)의 ARM 지원 여부: 스프링 부트 기본 구성은 문제없고, 새 의존성을 추가할 때 확인한다.

### 선택지 C: ARM 아키텍처, t4g.micro와 스왑 2GB

**설명.** 메모리 1GB인 t4g.micro를 쓰고 디스크 일부를 메모리처럼 빌려 쓰는 스왑 2GB로 부족분을 보완한다.

**장점.** 세 선택지 중 월 비용이 가장 낮다(t4g.small의 절반 수준).

**단점**

- 스왑은 디스크를 쓰기 때문에 메모리보다 훨씬 느리다. 배포 시점처럼 메모리가 모자라는 순간마다 응답이 눈에 띄게 느려진다.
- 스왑 설정을 빠뜨리면 배포 중 메모리 부족으로 스프링 프로세스가 강제 종료된다.

## 결정

우리는 ARM 아키텍처의 t4g.micro 인스턴스를 채택한다.

구체적으로 다음과 같이 구성한다.

- 서울 리전의 TECHCOURSE-PROJECT VPC, project-public-a 서브넷에 인스턴스를 생성한다. 아키텍처는 Arm(arm64), 유형은 t4g.small, 스토리지는 gp3 20GB, 키 페어는 ED25519, 보안 그룹은 project-public으로 잡고 지정 태그 3종을 붙인다.
- CI 워크플로의 `runs-on`을 `ubuntu-latest`에서 `ubuntu-24.04-arm`으로 바꿔 ARM 네이티브 빌드로 전환한다.
- ADR-01의 배포 이력에 `architecture` 값이 `arm64`로 기록되도록 맞춘다.
- 팀에 서버와 이미지가 ARM 기준이라는 사실을 공유한다.

이렇게 정한 이유는 다음과 같다.

- 성능은 t3와 동급이고 이미지도 논리적으로 같은 프로그램이므로 품질 차이가 없다. 공개 리포지토리라는 조건과 프리 티어 미대상이라는 조건을 확인하고 나니 전환 비용과 무료 역전 카드가 모두 사라졌다. 가격만 차이로 남았는데, 그 가격에서 t4g가 20퍼센트 싸다.
- CI 수정이 한 줄이라 ADR-01의 Build Once, Promote 구조를 그대로 유지한다.
- 현재 IAM 권한으로 EC2 생성이 가능해 추가 권한 요청 없이 실현할 수 있다.

나머지 선택지를 채택하지 않은 이유는 다음과 같다.

- **선택지 A.** 전환 비용이 한 줄로 끝난다고 확인된 이상 가격 말고는 우위가 없다. 결정 뒤에 확인한 계정 정책의 유형 제한 때문에 지금은 고를 수도 없다. 정책이 바뀌고 아래 재검토 조건이 생기면 첫 대안이 된다.
- **선택지 C.** 운영 서버의 배포 시점 지연과 강제 종료 위험을 월 만 원 수준의 절약과 바꾸지 않는다.

## 트레이드오프

### 장점

- 같은 성능을 월 5천 원가량 싸게 쓴다.
- CI가 에뮬레이션 없이 네이티브로 빌드하므로 빌드 속도가 떨어지지 않는다.
- ADR-01의 이미지 식별과 보존 구조를 수정 없이 그대로 적용한다.

### 단점

- 아키텍처라는 변수가 하나 늘어난다. 컨테이너가 뜨지 않는 장애가 생기면 아키텍처 불일치를 늘 원인 후보로 올려야 한다.
- x86을 전제로 한 외부 자료를 그대로 따라 할 수 없는 경우가 생긴다.
- CI 비용이 리포지토리 공개 상태에 묶인다.

## 후속 결정

- 탄력적 IP 할당과 도메인 연결, 리버스 프록시 구성은 별도 결정으로 다룬다.
- 서버가 여러 대로 늘거나 x86 환경이 추가되면 ARM판과 x86판을 함께 빌드하는 멀티 아키텍처 구성이 필요해진다. 이때 어느 판의 digest를 배포 이력에 기록할지는 ADR-01의 후속 결정과 함께 정한다.

## 구현 체크리스트

- [ ] TECHCOURSE-PROJECT VPC의 project-public-a 서브넷에 arm64, t4g.small, gp3 20GB, ED25519 키 페어로 인스턴스를 생성한다.
- [ ] 보안 그룹은 새로 만들지 않고 제공된 project-public을 선택한다. 생성 권한이 명시적으로 막혀 있다.
- [ ] 태그 `Service=techcourse`, `Role=techcourse-etc`, `ProjectTeam=팀 서비스 영문 이름`을 붙인다. 태그가 없으면 운영진이 리소스를 삭제한다.
- [ ] 키 페어 파일을 안전하게 보관하고 권한을 400으로 좁힌다.
- [ ] CI 워크플로의 `runs-on`을 `ubuntu-24.04-arm`으로 바꾼다.
- [ ] CI에 빌드된 이미지의 아키텍처가 arm64인지 확인하는 검사 단계를 추가한다.
- [ ] 배포 이력의 `architecture` 값이 arm64로 기록되는지 확인한다.
- [ ] 스테이징 배포로 컨테이너가 정상 기동하는지 확인한다.
- [ ] 완료 후 ADR 상태를 Accepted로 변경한다.

```
1단계: 인스턴스 생성과 SSH 접속 확인
2단계: CI를 ARM 빌드로 전환하고 이미지 아키텍처 검증
3단계: 스테이징 배포로 컨테이너 기동 확인
4단계: 운영 적용
```

## 검증 방법

이 결정이 실제 구현에서 지켜지는지 다음 방법으로 확인한다.

- CI에서 `docker inspect`로 빌드된 이미지의 Architecture 값이 arm64인지 검사한다.
- 배포 파이프라인에서 서버의 `uname -m` 결과(aarch64)와 이미지 아키텍처가 일치하는지 검사한다.
- 배포 후 컨테이너 기동 로그에 `exec format error`가 없는지 확인한다.
- 월 청구서에서 EC2 비용이 예상 범위인지 확인한다.

완료 기준은 다음과 같다.

- CI가 빌드한 이미지가 스테이징과 운영에서 수정 없이 기동한다.
- 월 EC2 인스턴스 비용이 t3.small을 썼을 때의 예상액보다 낮다.
- 배포 과정에서 아키텍처 불일치로 실패가 나오면 재검토한다.

## 롤백 및 재검토 조건

### 롤백 방법

1. x86(t3.small) 인스턴스를 새로 생성한다. 실행 중인 인스턴스의 아키텍처는 바꿀 수 없다. 현재 계정 정책이 t4g 계열만 허용하므로 x86으로 옮기려면 운영진 협의가 먼저 필요하다.
2. CI 워크플로의 `runs-on`을 `ubuntu-latest`로 되돌리고 이미지를 다시 빌드한다. 기존 ARM 이미지는 옮겨 쓸 수 없어서 새 digest가 나오고, ADR-01에 따라 배포 이력에 새로 기록한다.
3. 탄력적 IP 또는 도메인을 새 인스턴스로 옮기고 컨테이너 기동과 헬스체크를 확인한다.

### 재검토 조건

다음 상황이 생기면 이 결정을 다시 검토한다.

- 리포지토리가 비공개로 전환되어 ARM 러너 비용이 발생한다.
- 계정이 프리 티어 또는 무료 크레딧 대상이 되어 x86 무료 선택지가 생긴다.
- ARM을 지원하지 않는 네이티브 의존성이 필요해진다.
- ARM과 x86의 요금 차이가 사라지거나 역전된다.
- 서버 대수가 늘거나 멀티 아키텍처 구성이 필요해진다.
- 계정 정책의 허용 유형이나 네트워크 규칙이 바뀐다.

결정을 변경할 때는 이 ADR을 직접 덮어쓰지 않는다. 새 ADR을 작성하고 이 ADR의 상태를 Superseded로 변경한다.
