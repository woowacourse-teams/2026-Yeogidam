# ADR-01. InstagramUrl · MediaShortcode 모델링

- **상태** 결정
- **날짜** 2026-09-07
- **관련 명세** US-01 「지원하지 않는 링크는 접수하지 않고 사용자에게 이유를 알린다」

---

## 배경

Supabase로 돌아가던 여기담을 Java Spring Boot로 옮기면서 도메인 모델링을 시작한다.

문제는 시작점이었다. US-01 명세는 대부분 「공유한다·추출한다·저장한다」처럼 사용자가 하는 일로 적혀 있어서 문장 하나를 그대로 단위 테스트로 옮기면 여러 객체와 외부 API가 한꺼번에 얽힌 통합 테스트가 된다.

명세를 훑어보니 **외부 호출 없이 값만 보고 판단할 수 있는 규칙**은 하나뿐이었다. 「지원하는 링크인가?」다. 여기서 시작한다.

---

## 결정

### 1. 릴스와 게시글을 모두 받는다

받아들이는 URL 형태는 Meta가 직접 만든 워드프레스 플러그인 [meta-embeds-for-wordpress](https://github.com/facebook/meta-embeds-for-wordpress)가 명시한 것을 따른다.

```
게시물   https://www.instagram.com/p/{media-shortcode}/
릴스     https://www.instagram.com/reel/{media-shortcode}/
```

운영 데이터 383건이 `/reel/` 204건 · `/p/` 179건으로 거의 반반이다. 한쪽만 받으면 절반을 버리게 된다.

프로필 주소(`instagram.com/{username}/`)는 게시물이 아니므로 받지 않는다.

호스트는 `www.instagram.com`과 `instagram.com`을 모두 받는다. 운영 383건은 전부 `www`지만, `www` 없는 주소는 인스타그램이 301로 `www`에 보내는 같은 페이지라서(실측 2026-09-07) 수동 입력으로 들어와도 거부할 이유가 없다. 로그인 벽으로 보내는 `/reels/`와는 사정이 다르다.

**이 둘 말고는 받지 않는다.** 여기담은 모바일 앱이고 사용자는 인스타그램 앱의 공유 버튼으로 링크를 보낸다. 그 경로가 내주는 형태가 위 두 가지다(뒤에 `?igsh=...`가 붙지만 쿼리는 버린다).

아래 변형들은 **PC 브라우저에서만 생긴다.** 지금은 지원 범위 밖에 둔다.

| 변형 | 어디서 생기나 |
|---|---|
| `/reels/{code}/` (복수형) | PC 웹에서 릴스를 열면 주소창에 이 형태로 뜬다 |
| `/{계정}/p/{code}/` | 프로필 그리드에서 링크 주소를 복사할 때 |
| `/tv/{code}/` | 폐지된 IGTV의 잔존 경로 |

받지 않되 **버리지는 않는다.** 미지원 경로로 들어온 링크는 예외를 던지고(결정 6), 위층에서 어떤 형태였는지 로깅한다. 로깅 계층이 생기기 전까지는 예외 메시지에 입력값을 붙여 콘솔 스택트레이스로 관측한다. 값 객체는 로깅 프레임워크에 의존하지 않고, 메시지에 값을 실어 두면 어느 층에서 잡히든 정보가 따라간다. 실제로 들어오는 빈도가 관측되면 그때 지원 여부를 다시 판단한다. 지금 추측으로 넓히면 검증할 수 없는 분기만 늘어난다.

### 2. 식별자 이름은 `MediaShortcode`로 한다

Meta 문서가 `{media-shortcode}`라고 부른다. 도메인 어휘를 그대로 쓰고 `ShortCode`나 `Code` 같은 축약은 만들지 않는다.

### 3. `MediaShortcode`를 값 객체로 분리한다

원시값 포장 기준 세 가지를 모두 만족한다.

| 기준 | 해당 여부 |
|---|---|
| 검증 | 문자 구성 규칙이 있다 |
| 타입 안전 | `String`을 아무 데나 넘기는 것을 막는다 |
| 도메인 어휘 | Meta가 쓰는 공식 용어다 |

### 4. 문자셋만 검증하고 길이는 고정하지 않는다

검증은 두 가지만 한다.

- 비어 있지 않을 것
- `[A-Za-z0-9_-]`로만 이루어질 것

**길이를 빼는 이유 — 11자로 못 박으면 정상 링크를 거부한다.**

Meta README의 예시가 `https://www.instagram.com/p/fA9uwTtkSN/`인데 이 shortcode는 **10자**다. 직접 열어보니 지금도 살아 있는 게시물이었다. 우리 DB 383건이 전부 11자인 것은 최근 데이터에 치우친 표본일 뿐이고 현행 Supabase 파서도 길이는 보지 않는다.

**문자셋을 남기는 이유 — 인코딩 규격에서 나오는 값이다.**

shortcode는 미디어 ID를 base64url로 인코딩한 값이다. base64url 알파벳은 `A-Z a-z 0-9 - _`이고 이것이 `[A-Za-z0-9_-]`와 정확히 일치한다. 임의로 고른 범위가 아니다.

| 근거 | 확인 결과 |
|---|---|
| base64url 알파벳 | `[A-Za-z0-9_-]`와 일치 |
| 운영 DB 383건 | 383건 부합, 위반 0건 (밑줄 45건·하이픈 59건 실사용) |
| 현행 파서 `reel.ts:35` | `/^[A-Za-z0-9_-]+$/` |
| Meta README 예시 2개 | 둘 다 부합 |

길이는 관측에 불과했고 반례가 나왔지만, 문자셋은 규격이라 성격이 다르다. 이걸 빼면 `ABC?igsh=xyz`나 `AB%20C` 같은 값이 shortcode로 통과해서 인스타그램에 요청을 보낸 뒤에야 실패한다. 사용자는 「지원하지 않는 링크」 대신 알 수 없는 오류를 받게 된다.

길이 규칙이 필요해지면 그때 근거와 함께 넣는다.

### 5. `InstagramUrl`은 `MediaShortcode` 하나만 가진다

URL 문자열을 함께 들지 않는다. 이유가 둘이다.

**동등성을 shortcode 기준으로 잡아야 한다.** `/reel/{code}/`와 `/p/{code}/`는 같은 게시물이다. 실제로 두 형태로 각각 열어봤더니 인스타그램이 돌려주는 정규 주소가 14건 모두 같았다. URL을 함께 들면 같은 게시물이 다른 값이 되거나, `equals`에 참여하지 않는 필드를 두게 된다.

**경로가 도메인 의미를 갖지 않는다.** 릴스와 게시글을 모두 받기로 했으니 `/reel/`과 `/p/`를 나눌 이유가 없다. 게시물 종류는 어차피 URL로 알 수 없다(§부록).

URL이 필요하면 shortcode로 조립해서 내준다. 다만 응답에 조립 URL을 쓸지, 따로 보관한 원본을 쓸지는 아직 정하지 않았다(§남은 결정).

### 5-1. `InstagramUrl`은 record가 아니라 일반 클래스로 만든다

처음에는 record로 만들었다. `MediaShortcode`를 컴포넌트로 두고 `String`을 받는 부생성자를 더하는 방식이었다.

문제는 **생성 입구가 둘이 된다는 점**이었다. record는 컴포넌트와 같은 시그니처의 정규 생성자를 항상 만들고, 그것을 숨길 수 없다. 컴파일러가 거부한다.

```
error: invalid canonical constructor in record
  (attempting to assign stronger access privileges; was public)
```

그래서 `new InstagramUrl(mediaShortcode)`로 URL 검증을 건너뛸 수 있었다. 일반 클래스로 바꾸니 생성자가 `InstagramUrl(String)` 하나만 남는다.

부수적으로 얻은 것이 있다. record 시절에는 `this(...)` 위임 때문에 검증 메서드를 전부 `static`으로 둬야 했는데, 일반 클래스에서는 인스턴스 메서드로 쓸 수 있다. `MediaShortcode`와 모양이 같아졌다.

치른 값은 `equals`·`hashCode`·`toString`을 직접 짜는 것이다. `같은_shortcode면_경로가_달라도_동등하다` 테스트가 이 구현을 지킨다.

`MediaShortcode`는 컴포넌트 타입과 받는 타입이 `String`으로 같아서 compact 생성자로 끝난다. 생성자가 하나뿐이므로 record를 유지한다.

### 6. 예외를 사유별로 나눈다

명세가 「지원하지 않는 링크는 접수하지 않고 사용자에게 **이유를** 알린다」이므로, 이유를 구분할 수 있어야 한다. `IllegalArgumentException` 하나로 뭉치면 위층이 메시지 문자열을 파싱해야 하고 그건 값 객체가 만든 정보를 다시 잃는 일이다.

구분할 사유는 첫 테스트에서 드러나는 세 가지로 시작한다.

- 빈 값
- URL 형식 위반 (인스타그램 주소가 아니거나 파싱 불가)
- 지원하지 않는 경로 (프로필 주소 등 게시물이 아닌 것)

사유가 더 필요해지면 그때 늘린다.

### 7. 책임 경계

| 한다 | 하지 않는다 |
|---|---|
| URL 형식 검증 | 게시물이 실제로 있는지 확인 |
| shortcode 추출 | 영상인지 사진인지 판별 |
| 정규화 | 접수 여부 결정 |
| | 사용자에게 이유 알림 |
| | 중복 판단 |

가르는 기준은 **외부 호출 없이 문자열만으로 판단할 수 있는가**다. `InstagramUrl`는 예외를 던지기만 하고 그것을 접수 중단이나 사용자 안내로 바꾸는 일은 위층이 맡는다.

## 남은 결정

아래는 아직 정하지 않았다. 첫 테스트에는 걸리지 않으므로 필요해질 때 정한다.

**PC 브라우저 변형을 언제 지원할 것인가.** 결정 1에서 받지 않기로 하고 로깅만 한다. 로그에 실제로 쌓이면 그때 판단한다.

참고로 사용자가 각 형태를 손에 넣는 경로는 실측으로 확인했다.

| 어디서 | 얻는 주소 |
|---|---|
| **앱 공유 버튼** | `/p/{code}/?igsh=...` ← 여기담의 주 경로 |
| 검색 결과 링크 | `/p/{code}/` |
| 브라우저 주소창 | `/p/{code}/?img_index=1` |
| 프로필 그리드 링크 복사 | `/{계정}/p/{code}/` |

HTTP 리디렉트는 없고(`/p/`가 200 직행) 계정명 형태는 `og:url` 메타태그와 프로필 그리드의 `<a href>`에만 나타난다.

**원본 URL을 어디에 보관할 것인가.** 2026-09-07 러키와 논의했다. 러키의 물음은 「어차피 사용자한테 받는 값인데 왜 파싱해서 shortcode만 남기고 원본을 버리느냐, 받은 것을 갖고 있다가 그대로 내려주면 되지 않느냐」였다.

원본을 저장해야 한다는 데는 동의했다. 근거가 둘이다.

- US-01은 실패한 릴스도 「실패 항목으로 남는다 + 원본 릴스 링크」로 남기기로 했다. 파싱에 실패한 입력(프로필 주소, 만료 링크)은 shortcode가 없어서, 원본 문자열 없이는 「원본 릴스로 이동」 버튼을 만들 수 없다.
- 원본은 사용자가 준 사실이고 shortcode는 우리의 해석이다. 해석 규칙이 바뀌면(예: `/share/` 지원 추가) 과거 실패 건을 재처리할 근거는 사실 쪽에만 남는다.

어디에 둘지는 정하지 않았다. `InstagramUrl`에 `value` 필드를 더하는 안과 엔티티 쪽 문자열 필드로 두는 안이 있는데, 파싱에 실패한 URL은 `InstagramUrl` 객체가 아예 생성되지 않으므로 실패 건의 원본은 어느 안에서든 값 객체 밖에 있어야 한다. AC 「사용자는 실패한 원본 릴스로 이동할 수 있다」를 다룰 때 확정한다.

**응답에 내려줄 URL을 조립할 것인가, 보관한 원본을 쓸 것인가.** 조립한다면 `/reel/`과 `/p/` 중 어느 쪽으로 할지도 함께 정한다. 실측(2026-09-07, 요청 40회)으로 확인한 제약은 이렇다. 동영상이든 캐러셀이든 `/p/`와 `/reel/` 어느 쪽으로 열어도 200이 나오고 서버 리디렉트는 없으므로, 성공한 릴스는 어느 형태로 조립해도 동작한다. 반면 파싱에 실패한 릴스는 shortcode가 없어 조립이 불가능하다. 복수형 `/reels/`는 미디어 종류와 무관하게 로그인 벽으로 302를 보내므로 조립 후보가 아니다.

**`/share/...` 단축링크를 받을 것인가.** 리디렉트를 따라가야 해서 값 객체 밖의 문제다.

**`InstagramUrl`이라는 이름과 내부 상태가 어긋나 보이는가.** 이름은 URL인데 필드는 `MediaShortcode` 하나다. URL은 필요할 때 조립해 내주므로 모순은 아니지만 팀이 읽기에 자연스러운지 확인이 필요하다.

## 해소된 결정

전부 2026-09-07에 정했다.

**「로그인 필요」는 여기담 로그인이다.** Instagram 인증이 아니다. 이 값 객체와 무관하며 접수 유스케이스에서 다룬다.

**복수형 `/reels/`는 받지 않는다.** → 결정 1. 처음에는 받기로 했다가, 여기담이 모바일 앱이고 이 형태는 PC 브라우저에서만 생긴다는 점을 확인해 같은 날 뒤집었다.

**예외를 사유별로 나눈다.** → 결정 6

**원본을 저장하더라도 파싱은 필수다.** 러키와의 논의에서 「원본을 그대로 저장해 내려주면 파싱이 필요 없지 않은가」라는 물음이 나왔는데, 파싱의 목적이 URL 재조합이 아니라 동일 게시물 판정이라는 점으로 정리했다. US-01이 「중복 공유는 해당 장소를 최신순에서 상단으로 업데이트」를 요구하는데, 같은 게시물이 `/reel/{code}/`, `/p/{code}/`, `/reel/{code}/?igsh=...` 세 문자열로 들어올 수 있어 원본 비교로는 중복을 잡을 수 없다. 운영 383건에서 고유 shortcode가 364개로 중복 공유 19건이 실재하고, 현행 파이프라인도 완료된 분석을 shortcode 일치로 재사용한다.

## 부록. 인스타그램 게시물 종류

모델링하면서 확인한 도메인 지식을 남긴다. 실측 14건과 Meta 공식 문서 기준이다.

### 종류와 URL의 관계

| 종류 | URL | 미디어 수 | 비고 |
|---|---|---|---|
| 사진 게시물 | `/p/` | 1 | |
| **캐러셀** | `/p/` | 2~20 | 전용 경로가 없다 |
| 옛 동영상 게시물 | `/p/` | 1 | 2022년 7월 이후 신규 생성 불가 |
| 릴스 | `/reel/` | 1 | 지금 인스타의 유일한 동영상 형식 |
| IGTV | `/tv/` | 1 | 2022년 폐지 |
| 스토리 | `/stories/` | 1 | 24시간 뒤 소멸 |

**`/p/` 하나에 세 종류가 들어간다.** 캐러셀 전용 경로는 없다.

### URL로는 종류를 알 수 없다

실측 14건 전부에서, 같은 shortcode를 `/p/`로 열든 `/reel/`로 열든 인스타그램이 돌려주는 정규 주소가 같았다. 사용자가 어떤 형태로 복사해 왔는지는 종류와 무관하다.

종류를 알려면 인스타그램에 물어봐야 한다.

| 알고 싶은 것 | 보는 곳 |
|---|---|
| 릴스인가 아닌가 | 게시물 페이지의 `og:url`에 `/reel/`이 박혀 있는지 |
| 정확한 종류 | embed 페이지의 `data-media-type` (`GraphVideo` / `GraphSidecar` / `GraphImage`) |
| 슬라이드 장수 | embed HTML의 고유 `display_url` 개수 |

실측에서 캐러셀은 3~13장까지 나왔다.

### Meta API를 쓸 때 주의할 점

**릴스를 조회해도 `media_type`은 `REELS`가 아니라 `VIDEO`로 온다.** 릴스인지는 `media_product_type=REELS`로 판별한다.

**발행할 때 쓰는 이름과 조회할 때 나오는 이름이 다르다.** `CAROUSEL`로 올리면 `CAROUSEL_ALBUM`으로 읽히고 `STORIES`로 올리면 `IMAGE` 또는 `VIDEO`로 읽힌다. 열거형을 하나로 만들어 양쪽에 재사용하면 여기서 깨진다.

**Graph API로는 남의 게시물을 못 읽는다.** 자기 프로페셔널 계정이 소유한 미디어만 반환한다. 사용자가 아무 링크나 붙여넣는 여기담 시나리오에서는 쓸 수 없고 공개 게시물은 oEmbed로 가야 한다.
