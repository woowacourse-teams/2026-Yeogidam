# ADR-03. 연결 테이블 saved_place_share에 중간 객체를 두지 않는다, 승격 기준과 승격 시의 모양을 함께 정한다

- **날짜** 2026-09-09
- **관련** ADR-02(보관함 실체화), task 15, letter-to-lucky-saved-place-share.md

## 배경

saved_place_share는 저장한 장소(saved_place)와 공유 사건(media_share)의 다대다 관계를 해소하는 테이블이다. 같은 장소를 여러 공유에서 저장하면 연결이 여러 줄 쌓이고, 핀 상세에서 원본 릴스 목록으로 돌아갈 때 쓰인다. 여기서 물음이 나왔다. 테이블 세계에서 다대다가 중간 테이블을 요구한다면, 객체 세계에서도 중간 객체가 필요하지 않은가.

## 판단의 근거: 다대다와 중간 객체는 별개 문제다

관계형 모델에서 조인 테이블이 필요한 것은 구조적 한계 때문이다. 컬럼에는 컬렉션을 담을 수 없어서 N:M을 표현하려면 중간 테이블이 물리적으로 필요하다. 반면 객체는 참조와 컬렉션을 필드로 가질 수 있어서, 양쪽이 서로의 컬렉션을 참조하면 다대다 표현이 끝난다. "다대다라서 중간 객체가 필요하다"는 명제는 DB 진영의 이야기이지 객체지향의 명제가 아니다.

중간 객체가 등장하는 시점은 관계 그 자체가 의미를 가질 때다.

1. **관계가 속성을 가질 때.** 학생과 강의를 연결하는 순간 수강신청일, 성적처럼 어느 쪽 것도 아닌 데이터가 생기면, 관계는 연관 클래스(association class)로 승격된다.
2. **관계가 행위와 불변식을 가질 때.** "수강신청을 취소한다", "취소된 신청에는 성적을 못 준다" 같은 규칙을 양끝 객체에 밀어넣으면 응집도가 깨지므로, 관계 객체가 자기 상태와 규칙을 책임진다.
3. **관계가 도메인 용어일 때.** 수강신청, 주문항목, 예약처럼 현업이 이름으로 부르는 관계는 이미 하나의 개념이다.

DDD에는 이유가 하나 더 있다. 집합체 루트끼리는 객체 참조 대신 id로 참조하는 것이 원칙이라, 서로의 컬렉션을 직접 드는 대신 관계를 별도 개념으로 떼어내는 것이 경계를 깨끗하게 유지한다. 다만 에반스는 관계를 최대한 제약하고 의미 있는 관계만 명시적으로 모델링하라고 조언하므로, 모든 다대다를 기계적으로 승격하는 방향은 아니다.

## 현재 판정

saved_place_share는 (저장 id, 공유 id) 쌍이 전부다. 관계에 붙는 속성이 없고, 행위와 불변식이 없으며, 도메인이 부르는 이름도 없다(쓰임은 핀 상세의 조회 하나이고 조회는 record에서 응답으로 직행한다). 위 기준 어디에도 걸리지 않으므로 중간 객체를 만들지 않고, 연결은 영속화 계층(DAO와 스키마)의 사정으로 남긴다.

"같은 회원이 이 공유에서 이 장소를 저장했다"는 조건은 지금도 지켜진다. 보관함 upsert와 연결 insert의 입력이 도메인(SharedInstagramMedia.decidePlaces)이 실제로 전이시킨 placeId 목록뿐이라, 엉뚱한 회원이나 장소의 연결이 만들어질 경로 자체가 없다. 검증의 자리가 객체 생성자가 아니라 호출 흐름일 뿐, 규칙은 같다.

## 승격 트리거

다음 중 하나가 오면 중간 객체 도입을 다시 판단한다.

1. **연결을 만드는 경로가 둘 이상이 될 때.** 지금은 `savedPlaceDao.linkShare(savedPlaceId, shareId)`를 부르는 곳이 저장 흐름 하나뿐인데, 다른 서비스가 이 메서드를 부르기 시작하면 회원과 장소 검증을 빼먹은 호출이 가능해진다.
2. **관계에 속성이나 규칙이 생길 때.** 연결 정리 정책, 공유 삭제 기능이 생겨 고아 연결을 다뤄야 할 때 등이다.
3. **서비스의 검증 흐름이 읽기 싫어질 때.** 순서 보장이 코드에서 눈에 안 들어오게 되면 규칙을 한곳으로 모을 때가 된 것이다.

## 승격 시의 모양 (미리 명세해 둔다)

연결 객체(가칭 SavedPlaceRelatedMedia, 러키 temp-luckyy의 어휘)를 도입한다면 생성자가 "이 저장 장소와 이 공유를 연결해도 되는가"를 검사한다.

1. **회원이 같은가.** SavedPlace의 memberId와 SharedInstagramMedia의 memberId가 같아야 한다. 내 보관함 장소에 다른 회원의 공유를 연결하면 거절한다.
2. **그 공유에 해당 장소가 있는가.** 공유의 후보 중 SavedPlace의 placeId와 같은 장소가 있어야 한다.
3. **그 공유에서 해당 장소를 저장했는가.** 일치하는 후보의 상태가 SAVED여야 한다. 추출만 됐거나 버린 장소라면 거절한다.

추가로 객체가 null인지, DB에 저장된 id가 있는지도 확인한다. 저장 메서드는 원시값 대신 연결 객체를 받도록 바꾼다.

```java
var relation = new SavedPlaceRelatedMedia(savedPlace, share);
savedPlaceDao.linkShare(relation);
```

검증에 실패하면 객체가 만들어지지 않으므로 저장 메서드에 전달할 수도 없다. 생성자 검증을 우회할 수 없게 설계한다는 전제이며, 얻는 것은 호출자 실수 방지(새 저장 경로가 검증을 기억할 필요가 없음)와 규칙의 한곳 관리(변경과 테스트가 연결 객체 중심)다. 비용은 클래스와 전달 과정의 증가이고, 새 규칙이 생기는 것이 아니라 기존 규칙을 보장하는 위치가 달라지는 변화다.
